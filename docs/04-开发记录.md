# 读空气 开发记录

这是一份开发过程记录，不是设计说明。

它与文档规范有意冲突：按 [AGENTS.md](../AGENTS.md) §8，文档只描述最终状态，不保留历史方案、被取代的做法与修改过程；而本文恰恰要留下演进——比如"停止条件为什么从 2000 字改成了另一个值"，这类信息别处没有地方放，忘掉之后容易被重新提议。

因此本文的约定是：

- **当前的设计与结构以 [03-技术设计.md](03-技术设计.md) 和代码为准**，本文可能与其不一致；
- 做法变化时，在对应条目下补一行说明变化与原因，不改写原记录；
- 发现旧记录有明显错误时，就地加批注说明，不抹掉原样。

前半是已经开发过的做法与理由，中间是从开发过程中沉淀出的判断依据，后半是想法区——想到什么写什么，不代表已经决定。

## 一、已开发

### 后端：空气分析接口

| 做法 | 理由 |
| --- | --- |
| 公开契约只收页面文本，不收标题与地址 | 指标描述的是讨论自身的对抗性，是绝对值，不该随站点或话题缩放。实测带与不带这两项，评分没有实质差别 |
| 模型返回的分值越界时判为非法结果，不夹取到范围内 | 夹取会把一次失败的调用伪装成有效结论，宁可让这次分析直接失败 |
| 失败分成"内容不足"与"服务不可用"两类 | 前者要用户换页面，后者要用户稍后重试，提示、状态码、日志级别都不同 |
| "读不出来"是一等结果，不折算成分数 | 只有零散附和或导航文字的页面，曾经会拿到 0 分、置信度接近 1.0——用户读到的是"这里很平和"，实际含义是"读不出来" |
| 后端只给等级代码，中文措辞交给扩展 | 措辞会反复调整，不应进入契约 |
| 评分口径集中在一个提示词类里 | 换模型或调口径只动一处 |
| 内容下限与截断长度是暂定值 | 需要真实页面校准，预期会改 |
| 评测基线用三段样本跑真实模型，默认不进 CI | CI 没有模型密钥；只在改提示词或换模型时手动跑 |
| 评测样本从三段补到五段 | 原来只有平和、无法判断、对立三段，"争论明显"与"骂战激烈"两档没有基线。现在五段各对应一档（平和那段仍只断言上界：它的形状可能落在平和、也可能落在还算理性）。新增的两段是自造的——真实评论属于别人，不适合固化进仓库。两段都先跑真实模型把区间钉住：骂战那段 88/88/88（**最高档确实可达**，而真实样本里最激烈的一条也只有 72）；争论那段调了三版才落进档内——第一版太温和（28，还算理性），第二版让两人持续互怼又跳到 62（对立），最后是"有火气、有人站队、但不针对个人"（52/55/45）。这三版顺带说明档位之间差的是什么：不是话题多敏感，而是有没有开始针对人 |
| 评分校准一次：口径与分档都不动 | 用 5 段真实 B 站讨论各跑 3 次（手机推荐、扫地机选购、彩礼争论、油车电车之争、梅罗粉丝互撕，共 21 次调用）。分数依次 5 / 18 / 38 / 42 / 72，档位是平和、平和、还算理性、争论明显、对立明显——分得开，档位与内容也对得上。抖动：四段三次完全一致，只有最平和那段出现过 12/18/22，而它跨的那条线（PEACEFUL/REASONABLE，20 分）恰好不影响用户判断，两边都是"没事"。抖动远小于档位宽度（20 分），改提示词没有数据支持，所以不改。稳定本身是设计使然：模型侧 `temperature = 0`，剩下的是服务端的批处理差异。做法可复用：用扩展的抽取逻辑抓真实页面的讨论文本（剥掉抓取时加的头部、取前一万字），直接 POST 到本地后端，每段跑 3 次比极差与档位 |

### 扩展：骨架

| 做法 | 理由 |
| --- | --- |
| 点击工具栏时才注入内容脚本，不声明常驻脚本 | 常驻脚本在每个页面都会运行，与"仅在用户主动请求时读取页面"相抵；权限因此只需 `activeTab` 与 `scripting`，安装时不会要求读取所有网站数据。（后来加了按网站授权，见「扩展：进入网站时自动打开」：仍是用户看过哪一页才读哪一页，只是把权限换成了逐站申请） |
| 请求交给后台 Service Worker 发出 | 内容脚本受页面 CORS 限制，后台不受 |
| 浮窗渲染收在一个文件里，其余文件与 UI 无关 | 将来浮窗复杂度上来要换 UI 技术时，只替换这一层 |
| 后台、内容脚本与授权页各构建一趟 | MV3 的内容脚本不是模块，产物里不能出现 `import`，而 Vite 的多入口模式在 IIFE 格式下不可用，所以脚本各自打一份；授权页是普通扩展页面，按模块打包即可 |
| 单测只覆盖不依赖页面渲染的那部分 | 扩展第一次有自动化验证，此前全靠手工在浏览器里点。可测的是输入输出都是纯数据的那些：结果过期与整段被替换的判定、站点标识与权限模式、授权名单读写、后端返回体校验、两处存储契约（缓存记什么、隐私声明只取走一次）。依赖真实渲染的部分（shadow root、懒加载、`checkVisibility`）在测试环境里要么跑不起来、要么只是在测一个假的渲染层，那部分继续靠浏览器实测。CI 的扩展任务里加了 `npm run test` |
| 重复注入时复用宿主元素、换上新监听器 | 工具栏每点一次就会注入一次。"宿主元素在不在"不能代表"当前扩展上下文里有人监听"：扩展重新加载后，页面里还留着上一版脚本的宿主元素，旧监听器已经随旧上下文失效。曾据此提前退出，结果浮窗彻底打不开（后台报 `Could not establish connection`），只能靠刷新页面恢复 |
| 关闭浮窗要连"还在跑的那一轮"一起作废 | 分析要等好几秒，用户完全可能在这期间关掉浮窗，或者再点一次图标（每点一次都会注入一份新脚本）。光把 DOM 清掉不够：等回来的那段代码还在往同一个影子根里画，浮窗就自己回来了，两轮分析也会互相覆盖。现在每轮分析发一个凭据，收工（关闭、或换脚本接手）就清空，对不上就不再往下画。同一类收尾还有两处：渲染层关闭时要忘掉手里那份视图，否则授权一变的重绘会把它画回来；新脚本接手时让上一份停手，否则它还在轮询、还在等结论。凭据字段声明成可选，是实测出来的——扩展升级后页面里登记的上一版对象没有这个方法，直接调会让 `start()` 整个中断，浮窗再也打不开 |

### 扩展：页面正文提取

| 做法 | 理由 |
| --- | --- |
| 逐节点遍历并下钻 shadow root，不读 `body.innerText` | 视频站与论坛的评论正文常渲染在 shadow root 内，读 body 只能拿到页面框架 |
| 只把"渲染中"的元素算进正文，离屏元素照样算 | 判据是 `checkVisibility()`，它不把"在屏幕外"当不可见。实测视口下方 5000px 的元素仍返回 true；B 站评论区 17 条评论里 13 条在视口外，全部通过。这条是"滚动不会改变被分析那一段"的根基。唯一的例外是真正的虚拟列表（离屏节点直接从 DOM 移除），那种站点上窗口会随滚动变化 |
| "未就绪"与"读到空内容"分开判断 | 页面刚打开时讨论容器可能还没挂载，此时若回退整页，会把导航与推荐位当成讨论正文 |
| 站点差异集中在"站点期望表 + 通用回退"一处 | 只有一个实现时，接口形状取决于第二个站点的真实样子，现在抽接口等于先付一次、将来再付一次 |
| 第二个站点（知乎）落地：站点表只多一行，没有长出第二种形状 | 差异比预想的小得多。B 站的评论要进视口才渲染、内容区还藏在影子根里；知乎的答案在页面加载时就已经渲染好——实测问题页 10 条答案、约 2 万字，滚到底也不会变多，取到容器 `#QuestionAnswers-answers` 即可。想法区那条"等第二个站点落地再抽采集器接口"因此有了答案：**没有需要抽的东西**，`hostSuffix + selector（+ 可选的影子根内层选择器）` 这个形状两个站点都装得下 |
| 站点表按容器找，不按页面类型找：知乎只有问题页有那个容器，其余页面一律"没读到" | 实测知乎首页与热榜都没有这个容器（`main` 里分别是编辑器占位文案与标题列表，2697 与 12246 字），单回答页（`/question/X/answer/Y`）与专栏页也没有——它们给的是一份信息流或一篇文章，不是讨论。**没有站点表时，通用回退会把首页那 2697 字当成讨论送去分析**；有了这一行，这些页面与 B 站首页、会员购一样落回"没读到"。选 `zhihu.com` 而不是 `www.zhihu.com` 做后缀，是为了让子域（专栏）也走"没读到"，不再回退到整页 |
| 知乎的讨论是"回答"，不是"评论" | 知乎的评论要点开才加载，页面里根本没有——实测问题页上只有"20 条评论"这个按钮。所以能读的讨论就是那些回答，问题页上互相辩的也正是它们。零回答的问题页顺带验了：容器压根不渲染，落回"没读到可以分析的讨论内容"，不会把空态文案当成讨论 |
| 知乎不动行形态过滤 | 与 B 站相反的一份样本：知乎是长文答案，页面自己的文字（作者名、徽章、"N 人赞同了该回答"、推广行）实测只占容器字数的 **1.1%**（19735 字里 211 字），而 B 站短评论里的时间戳与控制词占 31%。过滤规则的依据是"吃掉多少窗口"，这里没什么可吃的，就不加站点专用规则 |
| 知乎用真实构建产物实测 | 问题页：送出 10000 字 / 683 行，含答案正文、不含问题头部（"被浏览""关注者"都不在），后端给 **58「争论明显」**（摘要："围绕隐私违规的激烈批评，讽刺较多但未成骂战"）；首页按自动打开触发：一个字都没送、浮窗没出现；零回答的问题页：面板停在"没读到可以分析的讨论内容"。做法：本地静态服务喂 `dist/content.js`，页面里垫一层 `chrome.*`，从 `__duKongQi` 的监听器触发。**知乎有 CSP（`script-src` 白名单）**，`addScriptTag` 注入会被拒，改走 CDP 的 `page.evaluate` 才进得去 |
| 微博只接移动站：桌面站的评论是虚拟列表 | 桌面站详情页的评论装在 `vue-recycle-scroller` 里——实测 DOM 里只留当前视口附近的 **2–9 条**，`scrollY` 0 → 1200 时可见正文 488 → 1554 字，而且**整批换人**（原先那条被移出 DOM）。这直接推翻"固定一万字窗口、滚动不改变被分析那一段"（正文提取那节里标过的例外），复带的后果更糟：滚动让基线行消失过半，会撞上"讨论换了一批"，用户刚开始往下读就把分数撤掉。所以 `weibo.com` 不进站点表。移动站相反：`.comment-content` 初次就渲染约 20 条，往下滚**只追加不回收**（卡片 23 → 42、2148 → 3103 字），与现有设计吻合。三条不同微博都命中同一个容器（21 / 21 / 23 个子节点） |
| 微博接上站点表后，样本从"整页"变成"评论区" | 没有站点表时通用回退取整页：同一页面送出 2104 字，混着正文与控件；接上后取 `.comment-content`，1228 字且正文与控件都不在样本里（后端给 12「基本平和」——这条微博本身温和，分数合理）。另一个例子更能说明问题：m.weibo.cn 首页以前会送出 48 字的整页文本并弹出浮窗，接上后落回"没读到"、自动打开时不出现。代价写在明处：桌面浏览器打开 m.weibo.cn 首页是"暂无数据"，移动站的入口主要靠分享与外链 |
| 面板报"读了约 N 条评论"，名词由站点给，不编一个通用的词 | 当初想把"N 字"换成"N 条"，是觉得条数更好懂；但三个站点读的根本不是同一种东西：B 站与微博读评论，**知乎读的是回答**——回答下面的评论要点开才加载，页面里没有。统一说"评论"在知乎上就是错话，统一说"内容"又等于什么都没说，所以名词跟着站点表走（`itemNoun`）。顺带把微博那一问记下来：**微博没有跨微博的评论**，评论挂在单条微博下；跨微博的往来是转发链（转发时自己写的那句），在 `.comment-content` 之外，我们没读 |
| 条数只数到窗口为止，没适配的站点不报条数 | 报出去的必须是结论真正覆盖到的那几条：知乎的问题页有几百个回答、一万字只装得下前几条，数整个页面就是替结论吹牛。做法是按顺序累加每条内容自己的文字，累过一万字就停。实测：知乎那个问题页容器里有 10 条回答，窗口装下 5 条 → 报"读了前面约 5 条回答"；微博 21 条、B 站 21 条（数字是楼层数，楼中楼不单独算）。没适配的站点报 null——通用回退取到的是 `main` 或整页，"一条内容"在那里无从定义，编一个数字只会让它显得比实际更可靠 |
| 那句写成"读了**前面**约 N 条"，不只写"约 N 条" | 因为数字会冻住：窗口一满，往下滑不再取进新内容，条数会一直停在同一个值（那条视频约 60 字一条，一万字大约停在 170 条——停在哪是个由字数决定、看着随机的数）。原来的措辞冻住时读起来像"这页只有 170 条评论"，而事实是"我们只读了前面这 170 条"；加一个"前"字就有了解释。顺带记下这条链路的真实观感：往下滑 → 提示"讨论有新变化" → 重算 → 条数变大 → **窗口满后连提示也不再出现**（样本一个行都没变，`hasContentChanged` 不触发），于是"数字冻住 + 系统沉默"。口径能被用户这样推出来不算问题——问题只是它冻住却不说为什么 |
| 界面文字按"行的形态"丢掉，不按站点结构丢 | 评论列表里混着页面自己的控件文字：时间、"共 70 条回复，点击查看"、孤立的一个"，，"、单独一个"回复"。两份真实样本实测各占 **31% 与 32%** 的字数——一万字的窗口有近三分之一被它们吃掉，而且相对时间还会随时间变，白给"讨论有没有变化"的比对添了噪声。判据用"这一行长什么样"而不是"哪个站点的哪个节点"：结构每个站点都不一样，而时间戳长什么样是通用的。用户名不在此列——它和"同感"这类短回复长得一样，通用规则分不开，只能靠站点结构识别（还没做）。实测同一段内容过滤前后：塌房那条 **62 与 72，同在对立档**，过滤后略高，因为同样的窗口里装进了更多真评论；华为小米那条两次落在 42–62 之间（那段本身就骑在档线上，看不出系统性差异）。过滤在 `dropUiNoise` 里，单测守着"短回复与句子里的关键词不能被误伤" |
| 提取起点收进评论列表内部，跳过列表头部的计数与排序控件 | 那些是页面控件，不是讨论内容 |
| 只取文本，不解析单条评论、用户名、点赞、楼层 | 逐条解析会把最容易变的 DOM 结构写进采集核心，而分析并不需要这些字段 |
| 不调用站点接口，不做签名与逆向 | 签名算法会变、要处理风控，而且它是站点专有的，换个站点等于重做 |

### 扩展：触发加载与等待

| 做法 | 理由 |
| --- | --- |
| 触发懒加载用"无感搬运"：给讨论容器加 `position: relative; top` 与 `opacity: 0`，只在视觉上把它挪进视口 | 评论要进入视口才加载，而滚动必然移动用户页面。相对定位不参与布局，容器原位与页面滚动位置都不变，用户察觉不到 |
| 用相对定位，不用 `transform` | 自定义元素默认是 inline，`transform` 对 inline 无效，得先改 `display`，那会引起重排 |
| 只在容器不在视口内时才搬 | 容器已经在视口里，说明页面自己在加载，此时透明化等于把用户正在看的内容藏起来 |
| 样式在结束时必须还原 | 否则容器会一直停在透明、不可交互的状态 |
| 面板显示中间态"正在读评论区…" | 搬运期间页面没有任何变化，缺少中间态会让用户以为点击没反应 |
| 停止条件是"样本 ≥ 2000 字且连着三次快照（间隔 500ms）一致" | 一读到内容就停，样本量会随加载进度浮动，同一页面的分数失去可比性。快照次数从两次加到三次，是因为评论分批到达、中间有间隙：只隔一次就开算，容易在间隙里"以为读完了"，随后又跳一次"讨论有新变化"。实测一份每 300ms 追加一批的页面，等到最后一批之后约 1.5 秒才开算，样本里包含最后一条 |
| 稳定判定不再附带字数门槛：连着三次快照一致就开算 | 上面那行里的 2000 字，实现上参与的是"能否提前结束等待"，于是样本本来就少的页面只能等满 8 秒。这与同一节下面"页面现成有多少就送多少，不因为不足 2000 字而空等"是矛盾的。实测一份 603 字的页面：用户看着"正在读评论区…"等了 8.5 秒，而那 8.5 秒里一个字都没再多。现在字数门槛只管"评论区够不够大、值不值得优先于整页"（因此改名 `MIN_COMMENT_SECTION_LENGTH`），等待只看"还变不变"——后者本来就管住了"评论还在往里加"。同一页面重测：8.5 秒 → 2.4 秒 |
| 讨论文本优先只取评论区，评论区不够大才退回整页 | 讨论是评论之间的事，而 `main`／`article` 里往往先是楼主正文——长正文会把一万字的窗口占满，评论区反而没入镜。够大（≥2000 字）才算数：评论区还没加载出来时容器里可能只有"评论"两个字，那时退回整页，有内容的判断总比没有强。实测一份"长正文 + 类名评论区"的页面，送出的样本里没有正文、只有评论 |
| 页面现成有多少就送多少，不因为不足 2000 字而空等 | 2000 字那道门槛管的是"要不要继续等"（评论区在懒加载时），不是"够不够格送"。页面本来就只有几百字时，等满 8 秒再给出同样结论更糟；判断内容够不够是后端的事，它会回 `insufficientContent`。曾经想改成"内容少时先等一会再送"，实测否掉了：B 站首批约 17 条评论、1886 字，把它带进视口再等 4 秒仍是 1886 字——更多评论只有真实滚动（滚到列表底部附近）才会追加，而那个动作按约定留给用户。所以等待在这个站点换不来内容，只会多等 |
| 采集有 8 秒总上限，超时就用已有内容 | 任何路径都不允许无限等待 |
| 没读到内容时只说没读到，不判断页面类型 | 原来是"评论还没加载出来。这个页面要滚到评论区才会加载，要我去读一下吗？"——它预设了滚一下就能解决，而视频站的首页、搜索、动态这些页面根本没有讨论区：用户按一次按钮，我们滚一趟、等 8 秒，最后还是同一句话，白等一次、信任掉一次。中途想过按页面类型分开说，判据用站点表里已有的那个容器（实测首页 0 个 `bili-comments`，视频页与番剧页各 1 个）——但那个判据是站点的，页面类型却是列不完的：同一个站点就有首页、搜索、动态、直播间、课堂、会员购……这张表补不全，还会随改版失效。最后只回答"读到了没有"：文案说"没读到可以分析的讨论内容。如果这一页确实有评论，我可以滚过去再读一次。"要不要再试交给用户，他就在那一页上。按钮也从"好，去读评论区"改成"好，试一下"——同样不该预设滚过去就有 |
| 授权站点上自动打开，只有读到内容才出现 | 这条规则不需要知道"哪一页该有讨论区"：拿提取结果说话，读到了才出现。以前是进站就画浮窗，于是首页、搜索这些页面会弹出一块"评论还没加载出来"，可用户并没有要求过什么。现在连"正在读评论区"也不闪——加载态是给点了图标的人看的，他没点，那行字对他只是闪一下。实测：首页自动打开时自始至终什么都没有；视频页自动打开照旧给出结果 |
| 等讨论容器的时间从 8 秒收到 1.5 秒 | 8 秒是整个加载预算，但容器在页面骨架里、加载完成时就已经存在（实测视频页与番剧页都是），后面填的才是内容。给容器留整个预算，只会让读不到内容的页面白等满 8 秒——而那种页面恰恰最多。这不是判断页面类型，是按实测给等待划一条止损线：容器更晚出现就让它更晚，用户自己滚一下也能再来 |
| 无感加载失败时退回真实滚动，且先给按钮由用户触发 | 位移必须由用户换来 |

### 扩展：分析链路

| 做法 | 理由 |
| --- | --- |
| 响应体在扩展侧过一道结构校验 | 后端是外部系统，返回结构不受编译期类型约束；缺字段或出现陌生的等级代码时，面板会渲染出 undefined 或空白 |
| 一次分析结论缓存在会话存储里，键取内容哈希 | 钱和等待都在模型那一侧，而"自动打开"让同一段内容被反复送：每进一次站、每刷一次页面都是一次调用。存在 `storage.session` 而不是内存，是因为 Service Worker 会被回收（内存缓存撑不过一次回收）；也不是 `local`，那样会攒出一份越积越旧、来路不明的结论。键取哈希而不是原文，会话存储里就不必再留一份讨论正文——实测存下的值里没有正文。实测：同一段内容问两次只发一次请求，换一段内容会另发一次；暂时性失败（服务不可用、网络不通）不记，否则一次抽风会让这个页面在整场会话里都不再尝试 |
| `host_permissions` 先只声明本机后端地址 | 部署地址确定之前不扩大权限范围 |
| 等级措辞与失败文案都放在扩展侧 | 后端只给代码与状态；措辞会反复打磨，不该进契约 |
| "服务不可用"与"网络不通"对用户合并成同一句 | 两者对用户是同一件事——过会儿再试——让他去分辨一个自己无能为力的差异没有意义。代价：与后台断连时同样无法从面板分辨，调试时曾因此多绕一步（日志里仍分得清） |
| 置信度低时只加一句"这里的内容不太好判断" | 用户不需要知道 0.85 这样的数字，只需要知道这次判断不太牢靠 |
| 改动 manifest 或后台脚本后必须重新加载扩展 | 这两样只在扩展加载时更新，而注入的内容脚本是按文件取的；调试时曾因此看到"面板已是新文案、后台却没有监听者"的假象 |

### 扩展：浮窗交互

| 做法 | 理由 |
| --- | --- |
| 位置与折叠状态放在渲染层的模块状态里，每次渲染再套回元素 | 面板每次状态变化都会整体重建，位置不能跟着丢 |
| 只有标题栏可拖，圆片整块可拖 | 正文里要能选中文字、点按钮；圆片没有别的内容 |
| 指针移动超过 4 像素才算拖动，否则当成一次点击 | 同一套指针处理要同时支持"拖圆片"和"点圆片展开" |
| 拖动时与视口变化后都把位置夹在可见范围内 | 否则浮窗会被拖出屏幕，只剩"再点一次图标"这种很隐蔽的恢复方式 |
| 浮窗自带 `position: fixed` 与最高 `z-index` | 宿主元素排在文档流末尾：少了定位，圆片会落到页面底部；少了 `z-index`，会被站点浮层盖住，连拖都拖不动——这两处都是实测踩到的 |
| 面板与圆片共用同一套表面：深色毛玻璃，带描边与背景模糊 | 收起前后应当是同一个东西；半透明必须配描边与模糊，否则它在浅色页面上会糊成一片 |
| 圆片保持中性，不按等级上色 | 客户端上的彩色块容易被读成游戏化的装饰，与工具的气质不合；"用颜色表达情绪"更适合交给一个有形象的角色，见想法区 |
| 四条边与四个角都能拖 | 拉窗口这件事，八个方向都得有；用户朝某个方向拖时不该什么都不发生。曾经只有左、右、下与两个下角，上边是后来补的 |
| 拖哪条边，对面的那条边就不动：拖左边缘时右边缘固定，拖上边缘时底边固定 | 拉窗口就是这么回事；若反过来（整个面板跟着动），手感会变成"在搬东西"而不是"在改尺寸" |
| 内容区独立滚动，标题栏固定 | 面板能被拖矮之后，内容必须能在里面滚，否则会把标题栏顶出去。实测拖矮后内容开始滚、标题栏位置不变 |
| 高度默认由内容撑，用户拖过之后才固定 | 内容长短不该由我们猜：默认贴合内容，用户拖过之后按他的意思来 |
| 宽高上限都跟着屏幕走，不设固定数值 | 曾经把宽度上限写成 460，实测中很容易撞到；上限应当表现为"到头了"，而不是"撞上一个数字"。宽度的上限是"两侧各留出贴边留白后还剩多少"，高度的上限是"顶边到屏幕底部还剩多少"，拖上边时则是"底边到屏幕顶部还剩多少" |
| 宽度下限 116px、高度下限 49px | 下限只留控件自身的尺寸：116 = 标题栏上四个 20px 按钮 + 间隔 + 内边距 + 描边，49 = 标题栏一行 + 上下内边距 + 描边。再小就有按钮被挤出窗口，用户丢的不是读数，而是"收起"这条回程。这个数改过四次：240（按可读性定的，属于替用户做判断）→ 80 → 72 → 94 → 116，第二三次下调出自"用户自己能判断、能撤销的事不该由产品锁死"，后两次上调都因为标题栏多了一个控件——控件变多，下限就得跟着走 |
| 窗口压到极小时内容被裁掉，而不是溢出边框 | 极窄极矮时子元素总要占地方。宁可裁掉（面板 `overflow: hidden`，内容区本来就能自己滚），也不要让文字和按钮飘到圆角外面去 |
| 窗口很窄时先牺牲标题，几个按钮始终留得住 | 下限要压到控件自身的尺寸，标题栏就得会退化。标题截断只是丢了个名字，按钮被挤出去就真的关不掉了。实测在最小尺寸（116×49）下四个按钮仍完整可点，标题宽度为 0 |
| 浮窗的落点与形态记在会话存储里，尺寸不记 | 落点是"这个窗口我想放这儿"，形态是"我想让它这样收着／展着"，两者都是用户明确做出的选择，记下来就不必每页重拖、重收（换页、换标签都沿用，浏览器一关回默认）。尺寸不一样，它跟着内容看，每次回到默认更省事，也不会出现"上次拖小到看不见"这种需要额外回程的状态。只存 `storage.session`，所以攒不出一份越积越旧的状态，也就不需要"恢复默认"——注意会话存储默认不对内容脚本开放，后台要显式放开 |
| 首屏落点距页面边缘 24px | 原来是 16px，右侧那条边离页面太近，看着挤 |
| 文字重排不做任何处理 | 宽度一变，浏览器就按新宽度折行、高度自己跟着变。实测 240 宽时面板高 248px，460 宽时 184px |
| 变宽越过右边缘时把面板整体左移，而不是限制宽度 | 面板默认就停在右上角，限制宽度会让它连默认宽度都回不去 |
| 缩放热区平时透明，指针压上去才显出一条边 | 它们不该破坏浮窗的外观，但也不能让人猜。原来是把显隐挂在面板的 pointerenter 上、手柄又是透明的，等于什么都没显（那对监听是空转的）；现在改成手柄自己的 `:hover` 加一层淡背景，指针压到哪条边哪条边亮 |
| 四边热区 10px、四角 16px | 6px 太细，不试一下抓不住；再宽就会吃掉面板内部的可用面积。这是"抓得住"与"不占地方"的折中 |
| 浮窗挂在影子根里 | 页面自己的样式再也渗不进来：继承类的（`body { letter-spacing }`）与伪元素类的（`li::marker`）原先都会影响浮窗。顺带给了样式表一个落脚处——滚动条、文字选中色这类内联写法表达不了的东西才写得进去。实测站点设了 `letter-spacing: 3px` 时浮窗仍是 `normal`。代价：定位、夹取这些逻辑不能再从宿主元素的子节点里翻，改成记住当前画出来的元素 |
| 分数与等级分开成两级：数字 26px、等级 13px 次要标签 | 原先两者同处一行、字号只差两级（16 与 14），扫一眼分不出哪个是结论。窄到放不下时让等级换行，而不是被裁掉 |
| 标题栏加一个"重新分析"图标 | 原来只有结果过期时才给重算按钮，想立刻重读只能再点一次工具栏图标——那是个藏起来的动作。三个图标仍画在同一块画布上，大小对齐 |
| 滚动条与文字选中色在影子根的样式表里改过 | 系统那条浅色滚动条压在深色玻璃上很扎眼；默认的选中蓝色也太跳。这两样都是伪元素，内联样式写不了 |
| 浮窗里的留白只留两档：行与行 6px，区域内部与区域之间 12px；标题栏下例外，给 16px | 原先标题栏到正文只有 6px、分隔线到设置区只有 8px，字和上下边界糊在一起；现在标题栏下 16px，分隔线上下、设置区到面板底边都是 12px（实测读数含 1px 分隔线，所以是 12 与 13）。标题栏下多给 4px 是因为正文第一行是 26px 的数字，方块大、行高又紧，同样 12px 看着就是贴着标题——实测按"看得见的边"算：图标底线到正文首行 17px、正文末行到面板底边 19px，两侧才基本对称。改的时候还发现按钮没有下外边距，"以按钮结尾"的视图（空态、失败态）比"以文字结尾"的少 6px，一并补齐 |
| 设置区与正文之间用一条细线隔开 | 只靠拉开距离在 280px 宽的浮窗里不划算——细线加上下各 12px 比单纯留 24px 空更省地方、也更好认。线用的是面板描边那档白（`rgba(255, 255, 255, 0.1)`），不引入新颜色 |

### 扩展：结果过期检测

| 做法 | 理由 |
| --- | --- |
| 比对范围就是被分析的那一段：扩展自己截取前 10000 字发出 | 后端那道截断只是兜底。若比对整页，用户只是往下翻、让窗口之外加载出更多评论，也会被提示"内容变了"，而分数本来就没覆盖那些内容 |
| 基线取刚送去分析的那段文本，而不是分析返回后重读页面 | 分析与返回之间页面可能又加载了内容，那些内容并没有被这次分析覆盖，不该被当成已分析 |
| 比对按行集合做，只看新增行 | 评论逐条出现，新出现的行才说明分析覆盖的那段变了。变多走这条判断 |
| 结果作废分两种：变多 与 整段被换掉 | 原来两者走同一条判断（只看新增行），于是换排序之后旧分数还留在浮窗上。可按本页上面那条原则——"整页换掉时不给旧分数，那个分数与当前页面的讨论毫无关系"——同一页里被分析的那批评论整段换掉是同一件事的站内版本：一条都不在眼前了。现在分开：评论变多 → 保留分数 + 提示重算（那段还在，只是又长了）；被分析那段的行消失过半（换排序、换筛选）→ 撤掉分数，只问"讨论换了一批，要重新分析吗？"，与换页同样处理。判据用"消失"而不是"新增"：换排序后新来的一批当然也是新的，但真正说明"换了"的是原先那批不见了；评论自然增长时旧行都在，它恒为 false。实测（同一视频、最热↔最新）：两份样本行重合度 17%，切换排序后 13 秒内浮窗给出替换提示且不再显示旧分数；人工追加 15 条评论仍走"变多"分支、分数保留 |
| 阈值：新增行 ≥ 10 条，或新增行占当前行的 20% | 绝对值管大页面，比例管小页面。两个数都是初值，要用真实使用校准 |
| 只比够长的行（≥ 8 字） | 相对时间（"3分钟前"→"4分钟前"）与点赞数这类短行每次刷新都可能变，攒几条就够凑到阈值，于是讨论没变也提示重算。代价：短回复（"同感"）不参与比对——它们本来也构不成"变化大"。实测：20 条时间戳同时变不触发提示，另添 10 条长篇评论才触发 |
| 只有样本真被窗口截断时才丢掉最后一行 | 原来无条件丢，等于"最新那一条评论"永远不参与比对：刚好新增 10 条时永远差一条、凑不到阈值。实测修好后，恰好 10 条长篇新评论能触发提示 |
| 换页判断只比 `pathname` | 站点常在 query 里追加跟踪参数（B 站的 `vd_source`、`spm_id_from`），比较完整地址会把它们误判成换页。实测 B 站切换评论排序也不改地址，所以排序变化会落到内容判断上，不会被误报成换页 |
| 同页内容变化时保留旧分数，只加一句提示与重算按钮 | 那个分数没有错，只是样本变了；而整页换掉时不给旧分数——它跟当前讨论毫无关系 |
| 比对周期 10 秒，且只在页面可见时执行 | B 站一次加载 20 条评论，比这更频繁没有意义；页面不可见时用户在别的标签页上，更没必要读这个页面 |
| 放弃"先看廉价信号、再比行集合"的两段式 | 廉价信号（容器子元素数）会漏掉"回复被展开"这类变化，而完整比对本来就要遍历一次 DOM，省不掉；10 秒一次的开销可以忽略 |

### 扩展：进入网站时自动打开

| 做法 | 理由 |
| --- | --- |
| 按网站逐个申请 host 权限，不在安装时就要全站权限 | 安装时的"读取您在所有网站上的数据"会吓到人，也与"仅在需要时读页面"的立场相抵；逐站申请时，那句权限提示就只讲那一个站点 |
| 请求授权落在一个扩展页面上，标题栏上那个设置图标只负责开合 | 请求 host 权限必须在用户手势里发起，而它长在内容脚本里，没有 `chrome.permissions` 这个 API，从后台的消息处理器里调也不算手势——Chrome 只认扩展页面上的那次点击。这不是设计选择，是平台规矩 |
| 授权界面嵌在浮窗里，而不是另开一个窗口 | 嵌进来之后"再点一次收起"是自然的，独立窗口做不到这件事：每点一次就多一个，用户得自己去收拾。外观上也更整齐——窗口自带系统边框，那圈边框会把一块界面切成好几段 |
| 嵌入页面自报高度 | 跨源文档之间量不到对方的高度，只能由嵌入页报回来；面板据此预留位置。两端都要认来源：嵌入页发的时候指名目标（父页面的来源），面板收的时候校验来源、窗口与消息形状，三样都满足才算数——这道校验真的会拦人，实测从页面本身伪造同样内容不会生效 |
| 嵌不进来就退到独立窗口 | 站点可以用 CSP 挡掉嵌进来的扩展页面，而那一步是静默的。等不到高度就把设置区换成一句"设置区加载失败"加一个按钮，走兜底路径——宁可多一次跳转，也不要用户对着空白的区域猜 |
| 失败文案只说哪一块没成，不猜原因、不把责任推给站点 | 早先写成"这个网站不允许读空气在这里显示设置"，把原因归到站点上：用户更信站点，这句话读起来像是我们被站点拒了。何况失败未必是站点的原因（也可能是扩展页面自己没起来），我们本来就不知道，写"设置区加载失败"最准 |
| 嵌入模式去掉自己的底色、标题与站点说明 | 面板已经有底色与标题，嵌入页再画一遍就会切出一块，接缝就是这么来的；站点说明也是多余的——这一小块就长在当前页面上，管的就是当前这个站 |
| 嵌入模式不再限宽、不再居中 | 那个 520px 限宽加自动边距是给整页设置页写的；嵌在浮窗里时，浮窗多宽它就多宽，文案与按钮一律和正文一样靠左 |
| 文案按"标准叫法 + 只说管什么"来写 | 标题栏那个图标把面板缩成一枚圆片，圆片还在原地、点它自己还原，所以提示写"收起"：不是传统意义的"最小化"（那是收进任务栏再从那里取回），也别用"折叠"（那个词在界面里多指文本区块）。"收起"还和圆片上的"展开读空气"配成一对。设置区那边同理——"开启后……""关掉即可"是在重复标签、按钮与图标已经说清的事，都不写 |
| 设置区的标签要说出被打开的是什么，也要限定范围 | 一是"进入网站时自动打开"没说打开什么，得写到"打开读空气"；二是这个开关只管当前这个站，所以写"当前网站"而不是泛指的"网站"。标签、控件、图标各说一件事，不互相重复 |
| 状态用开关，不用"开启/关闭"两个按钮 | 动词按钮要求用户把动词反过来读才能知道当前状态（按钮写"关闭"才说明现在是开的）；开关蓝开灰关，状态自己说话，标签也可以安心写"这段设置是什么"。列表页保留"关闭"按钮——那里做的是"把这个站点移除"，不是翻一个布尔值 |
| 授权页的标题写"设置"，里面则说清是哪一项 | 它管的是设置、不是读空气本身，所以叫"设置"不叫"读空气"；但同一个页面里不再重复"设置"——标题栏已经说过一次了，内容直接说是哪一项（"进入当前网站时自动打开读空气"），下面一行放站点与开关。只有完整的设置列表页保留"设置"做标题：那一页确实装着所有设置 |
| 兜底窗口沿用浮窗那一套外观：同一个渐变、同一套字号、同一个强调色 | 它是同一个产品在说话，不该长得像另一件东西。最初用的是浅色网页样式，与浮窗割裂 |
| 兜底窗口落在当前窗口的中上位置 | 不指定位置时由系统决定，实测跑到了屏幕左下角——既不像一次提问，也离用户正在看的地方远 |
| 授权页不自己关 | 开关都长在这一页上，一关就断了来回改的路径，也让没看清的人以为没办成。嵌在浮窗里之后更没必要关——那个设置图标本身就是开合 |
| 隐私说明放在设置页里，商店页面之外 | 讨论内容会离开浏览器，这件事得在用户能随手打开的地方说清楚。三件事按用户会问的顺序写：发什么（当前页面的讨论文字，开头一段）、服务器留不留（不保存）、什么时候发（你点了分析，或打开你授权过的网站）——最后一条顺带把"不想要就关掉上面的开关"这条回程指出来。服务器不落库、日志只记失败原因，这两条是读过代码确认的，所以文案可以照实写 |
| 隐私说明改到第一次拿到结论时说一次，设置页里撤掉 | 上面那条的原文案与理由。撤掉是因为设置区是调开关的地方，两段说明塞在开关下面像本说明书；更主要的是时机不对——这件事只在第一次发生时有告知价值，那时用户还不知道"分析"意味着文字要出本机，再往后它已经是常识。位置也就跟着定了：说在结论下面，正好落在那次外发的结果上，看完关掉即是收场。说过没有记在 `storage.local` 里（不能记 session：那样每开一次浏览器都要再说一遍），且是显示的那一刻就记下——只读不写会让说明变成每次都出现。存储不可用时宁可不显示，同样是为了不退化成一分析就说一遍 |
| 隐私说明的门从"拿到结论"改到"发出请求" | 上面那行说"说在结论下面"，实现时就顺着挂成了"只有成功才说"，这是错的：文字离开浏览器发生在请求发出的那一刻，与模型答没答出来无关。第一次分析撞上"内容太少"时，文字照样到了服务器，回来的是失败——此时不说，就得等到某次成功才补上，告知晚于事实就不叫告知了。现在它挂在真的发出过请求的结局上：拿到结论说，这次发送失败也说；"评论还没加载出来"这类根本没发请求的状态不带它 |
| 隐私声明显式标出"隐私说明"，措辞不绑定当前页面 | 原来它只是一句陈述句，混在分析结果里读着像结果的又一句——没人知道这是一条声明，所以开头补上"隐私说明："并加重一点。措辞也把"这一页"改成了"网页里的讨论文字"：声明是通用的，说"这一页"会让人以为换个页面看就不作数了 |
| 隐私声明改成面板里的一块区域，排在设置区下面 | 上面那条是把声明做成了结果里的一行，靠"隐私说明："开头自报身份；但一行字夹在结果里，怎么改都还是像结果的又一句，而且它本来与"这一次的结果"无关，位置不该跟着内容长短走。现在它是面板自己的区域：标题单起一行（"隐私声明"），标题右边是关闭，上面一条分割线，排在设置区之后；间距沿用设置区那一套——线上的 12px 来自上一块自带的 6px 与这里的 margin-top，线下 12px 是它的 padding-top。放在面板层而不是可滚动的正文层，是为了它不会被长结果挤出视野 |
| 再给隐私声明加一个设置里的入口：点开就地展开，不写"只显示一次" | 上面两条给的都是一次性提示，它的弱点在错过就没了：用户事后想确认"到底把我的什么发出去了"时无处可看。而声明本来就该是能反复引用的文档，不是只在某一刻闪一下的通知。两件事各管一半——提示管"第一次发生时知情"，入口管"事后可查证"；入口藏在设置图标后面，替不了提示，所以两个都留。两条具体取舍：两处措辞集中在 `shared/privacy`，免得一处改了另一处没改；入口是就地展开、不是再开一个页面（标签页每点一次多一个的教训）。没有在文案里写"该声明只显示一次"——它对用户没有决策价值，一句话的版面该留给"发了什么、留不留"；怕错过就用入口解决，不靠提前打招呼 |
| 隐私声明的措辞重写一版，并补上回程 | 上一版三句各有一处毛病。一，"发送到服务器判断"与"判断由外部模型服务完成"前后打架：第一句替服务器认领了判断，第三句又说判断在模型那边，读者只会觉得两句话对不上——现在第一句只说到"发送到自己的服务器"。二，收尾"由该服务的策略决定"读着像免责：被动句、两个分句都用"由…"收尾，还点不清我们到底知道什么；改成"模型服务那一环是否留存，由它的政策决定，我们无从确认"，把话落在"我们不知道的是哪一环"，而不是"不归我管"。三，三句都在讲我们会怎样，没有一句讲用户能怎么办——补一句回程（不想自动发送，在设置里关掉）。另外，"外部"改成"第三方"（与"自己的服务器"对照），不写具体服务商：点名更实在，但换个供应商就要改文案 |
| 授权名单记在 storage 里，而不是每次去读已授权的 host 权限 | 内容脚本要拿它决定设置图标染不染色，而它读不到 `chrome.permissions`；storage 的变更通知还顺带解决了"授权完成后图标要跟着变" |
| 自动打开的开关放在标题栏的设置图标里，不放正文下方 | 最初它在正文下面占一行，读起来像分析结果的一部分，位置还跟着内容长短浮动；标题栏才是面板自身控件的地盘，正文只放分析内容。代价是标题栏控件从三个变四个，尺寸下限跟着抬头（见上） |
| 授权页里的底色一律不透明 | 次按钮与开关轨道原来是半透明白，衬在渐变上颜色会随位置变，静态分析也算不准对比度（会被判成浅字压在浅底上）；换成同色相的不透明值，观感几乎一样，读数也确定 |
| 设置图标兼作状态：本站已开启时染成强调色，设置区展开时带一层底色 | 原来"已在本站自动打开"是一行字，去掉后状态就没地方说了。染色的对比度约 7:1，扫一眼就能看出这个站是不是开着 |
| 图标用两根滑杆，不用齿轮 | 16px 下画齿轮（圆加一圈齿）在线条风格里会糊成一团；滑杆四条线段画得准，也更像"这里是一小块设置"而不是"打开完整设置页" |
| 触发点选"页面加载完成"，不理会站内换页 | 站内换页（地址变了但没有重新加载）已经由浮窗自己的"页面换过了"兜着，这里再插一脚就是两套逻辑做同一件事 |
| 不申请 `tabs` 权限，未授权站点的地址读不到 | 权限最小化，而且它正好就是功能的开关：看不见地址就注入不了，不必再写一层"这个站点允不允许"的判断 |
| 已授权的站点每次加载都会重新分析一次 | 这是"进站即读"的代价，结果还没有缓存可复用（缓存是后面的事）。关掉浮窗不会改变这一点，要停就去设置里关掉这个站点 |
| 浮窗里压在毛玻璃上的浅色文字，透明度不低于 0.8 | 毛玻璃的底色跟着页面走：0.6 在亮页面上会把 13px 字的对比度压到 4 左右，正好卡在 4.5 这条线下面。底部那一行原来就吃这个亏，后来它整个挪进了标题栏 |
| 设置页暂时不做「恢复默认设置」 | 起初的想法是给一个动作收场：一次把所有站点都关掉。后来发现它服务的问题还不存在——窗口尺寸并不记忆，每次打开都是默认，授权也能逐个关掉，所以先不做 |
| 关闭的两步收在 `shared/auto-open` 里，开启拆在页面里 | 关掉一个站点 = 名单去掉 + 权限还回，两步分开写迟早会漏一步；而"开启"做不到合并——请求权限必须在用户手势里发起，只能由页面自己调 |

## 二、过程中总结出来的判断依据

有一些判断是从具体做法里归纳出来的，它们不描述当前项目长什么样，只回答"这类事往哪边定"。产品设计文档写当前设计，这类总结放这里。

**强制只用在不可逆的地方。**

用户自己能判断、能撤销的事，不由产品替他锁死：窗口能拖到多小、要不要自动打开、要不要重算，都是他的事。产品只守住真正越不过去的那条线——窗口小到控件自己装不下就不能再小，因为那时他连"收起"都点不到，丢的不是读数，是回程。

**给了控制权就要给回程。**

只给开关不给撤销，不是授权，是甩锅。每个"打开"旁边都该有"关掉"。

按这两条定下来的地方：

* 浮窗尺寸不设偏好性的上下限，唯一的下限来自控件自身的尺寸；
* 按网站授权，也能按网站关掉；
* 结果过期只提示，不自动重算。

## 三、想法区

**这一部分不受文档规范约束：想到什么写什么，包括可能不靠谱的。写在这里不代表已经决定，回头翻的时候按当时的情况重新判断。**

### 想过，还没定

- **桌面吉祥物**：用颜色表达情绪这件事，更适合交给一个有形象的角色（QQ 宠物、瑞星小狮子那种路子：心情好偏蓝绿，生气就红温），而不是撒在控件上的色块。MVP 不做，先记着。
- **分数该测哪一段（已定）**：曾经在"固定取开头一万字"与"跟随阅读位置"之间摇摆。现在定成：**固定取开头一万字，但起算点优先锁在评论区**（评论区不够大才退回整页）。理由：窗口跟随阅读位置会让同一页面出现两个分数、跨页面也没法比，而"正文把窗口吃掉"这个真问题用起算点就能解决；一万字本身先维持，长度每翻一倍钱与时延都涨，代表性更多取决于起算点而不是长度。还有一条更硬的理由：比对是拿"被分析那一段的行集合"做的，窗口一随位置移动，滚动本身就变成"变化大"——每次滚动新窗口与旧窗口的行大多不重合，直接越过阈值。要让跟随位置成立，就得连"什么算变化"一起重定义（例如把用户滚动不算变化，改看"这段区域里又来了新评论"），而那时滚动换段又变成"要不要重算"的新问题。固定窗口没有这个纠葛：抽取不看视口（见正文提取那节的实测），滚动本身不改变被分析的那一段。
- **自动重算（已定：不做）**：体验最好，但要额外授权（点过一次分析不等于授权持续把页面内容发往服务器）、要控制成本，还得让分数变化看得见。仍只做提示——重算要花钱，而"要不要多看一眼"用户一眼能判断。
- **2000 字 / 500ms / 8 秒这组数值的现状**：2000 那道门槛已从等待条件里拿掉（见正文提取那节），现在只管"评论区够不够大、值不值得优先于整页"；500ms×3 次快照实测够用（分批到达的页面在最后一批之后约 1.5 秒开算）；8 秒总预算很少用满——实测自带评论的页面 2.4 秒就出结果，用满 8 秒的情形只剩"容器在但内容一直没挂载"。
- **静默加载更多页**：把"下一页"也搬进视口就行，但样本会从三千字涨到几万字，直接撞上后端的 10000 字截断。要不要做取决于截断怎么处理。
- **后端 10000 字截断是否改成均匀取样（第四次尝试：暂时不改，只剩"窗口内突变"没覆盖）**：前三次都败在同一个地方——样本在"氛围"这个维度上是均匀的（三次的数据见"记下来的数据"那节）。第四次换思路，按"塌房明星"找：一条 308 万播放的视频，评论跨 2022 年塌房当时到 2026 年，共 23705 字。三千字窗口给 42 与 62，说明**样本内部确实不均匀**；但一万字的两个不重叠窗口都是 62——**一万字把这种缓慢的时间漂移摊平了**：前一万字已经跨了四年，新旧两段都装了进去；窗口再短（三千字）就会得出不同结论。仍未覆盖的是"窗口内突变"：反转刚发生、新评论还没占满一万字时，窗口里旧风向仍占多数，我们会报旧气氛。这类样本有时效性，得在事件刚发生后抓，还没遇到。

### 记下来的数据

- **评测基线的完整核验（五段样本，各跑两次）**：平和 5/5、争论 45/58、对立 78/78、骂战 88/88，只有附和那段两次都回 422「页面内容不足以分析」——五条断言全部成立。两处值得留意：**"对立"那段贴着自己档位的最上沿**（78，上界 80），下次改口径时它最可能先变红；"争论"那段两次差 13 分（45 与 58），仍在档内但余量不大。
- **响应速度基线**：点击图标到浮窗出现几乎实时；"正在读评论区"基本感知不到（该页面的评论已经加载好，这步被直接跳过）；"正在判断空气"约两三秒——用户的等待几乎全部来自模型判断。以后调优拿它对比。
- **评分校准的实测（B 站真实页面）**：5 段讨论文本各跑 3 次，分数 5 / 18 / 38 / 42 / 72；同段重复：四段三次完全一致，只有最平和那段出现过 12/18/22。模型单次判断耗时（5–10k 字输入）0.6–1.3 秒，比上面那条"两三秒"快——那条是在整条扩展链路上量的，含消息往返。
- **等待耗时的实测**：内容已渲染的页面，点图标到出结果不到 1 秒；需要把评论区搬进视口并等它渲染的页面约 2.4 秒（其中等稳定 1.5 秒、模型判断约 1 秒）；改掉字数门槛之前，同一页面要等 8.5 秒。分批到达的页面（每 300ms 一条、共 10 条）：最后一条之后约 1.5 秒开算，样本里包含最后一条。
- **换排序的实测（两段视频）**：
  - 彩礼那条（5556 字）：最热与最新两份样本的行重合度 17%，分数 38 与 42。两批评论都是同一话题的争论、氛围相近，**不能据此推论"分数对抽到哪一批不敏感"**。
  - 华为小米那条（最热 7957 字、最新 14286 字）：最热 **42**、最新 **62**——差 20 分、跨一档（"争论明显" → "阵营对立"）。机理清楚：最新排序的前排是近期短促的对骂（"太搞笑了吧"），最热的前排是高赞的长篇数据对比（营收、纳税数字）。**所以"取到哪一批"确实能改变结论。**
  - 顺带：这个 42 与 62 的落差正好落在新加的"讨论换了一批，要重新分析吗？"上——切排序后旧分数撤掉，用户不会看到"42 怎么突然变成 62"。
  - 排序切换不改地址，所以不会被当成换页，会落到内容判断上。
- **截断代表的实测（四次尝试）**：
  1. 一段整体平和的视频，前/中/后三个一万字窗口：5/5、5/3、3/0——氛围本来就均匀，问不出什么。
  2. 同一视频换排序（内容只重合 17%）：38 与 42——两批氛围相近，同样不能作证。
  3. 一段跨度八个月、内容从长篇数据对比到短促互撕的样本（14286 字），两个完全不重叠的 7000 字窗口：62/62 与 62/58——位置差异 0–4 分，但两段氛围本身都是对立，样本在"氛围"维度上仍均匀。
  4. 塌房明星那条（23705 字，评论跨 2022 年塌房当时到 2026 年）：三千字窗口前段 42、后段 62（差 20 分、跨一档，**样本内部确实不均匀**）；一万字窗口前段 62/62、后段 62/62（完全一致）。与直觉相反：最激烈的是塌房当时的 2022 年（粉丝与路人对立，有"二椅子""去S"等侮辱词），四年后的围观反而平静。

### 想过，目前不做

- **逐条评论解析、按条数计数（20/50 那种）、文本去重**：去重会削掉"一大片同感"这类本该计入的样本。
- **MutationObserver**：新建的 shadow root 不会触发宿主上的 observer，"发现新 shadow root"本身还得轮询——除非去改页面主世界的 `attachShadow`。
- **采集器接口 + 每站一个实现类**：等第二个站点真的落地，看两者的差异长什么样再抽。**知乎落地后看过了：不抽**——两者的差异只有"多一个影子根内层选择器"与"要不要无感加载"，站点表多一行数据就装下了，没有可抽的接口。
- **`scrollIntoView` 触发 + 采集后恢复滚动位置**：被无感搬运取代，连"恢复位置"这个需求一起消失。
- **进入页面就自动采集或预热**：与"仅在用户主动请求时才把内容发往服务器"冲突，而且自动触发必然移动页面。
- **固定条数上限**：停止条件已经是"够样本且稳定"，条数上限是同一意图的另一种表达，不必并存。
- **通用爬虫框架、事件总线、插件系统**。

### 还没验证

- **真实点击工具栏**：受扩展权限模型限制，需要用户手势，我模拟不了。
- **兜底滚动路径**：缺一个能让无感加载失败的真实页面。如果各站点都支持无感，这条路径可能变成死代码。
- **加载很慢 / 评论区始终不出现 / 评论数量不足**这三种情形。
- **SPA 切换视频**：等过期检测实现后一起验。
