# 读空气 开发记录

这是一份开发过程记录，不是设计说明。

它与文档规范有意冲突：按 [AGENTS.md](../AGENTS.md) §8，文档只描述最终状态，不保留历史方案与修改过程；而本文恰恰要留下演进——比如"停止条件为什么从 2000 字改成了另一个值"，这类信息别处没有地方放，忘掉之后容易被重新提议。

因此约定：

- **当前的设计与结构以 [03-技术设计.md](03-技术设计.md) 和代码为准**，本文可能与其不一致；
- 做法变化时，在对应条目下补一行说明变化与原因，不改写原记录；
- 只在有判断价值的地方留历史：纯粹被推翻、又没留下教训的中间态，不留；数值与样式细节能从代码读到的，也不留。

前半是已经开发过的做法与理由，中间是过程中沉淀出的判断依据，后半是想法区。

## 一、已开发

### 后端：空气分析接口

| 做法 | 理由 |
| --- | --- |
| 公开契约只收页面文本，不收标题与地址 | 指标描述的是讨论自身的对抗性，是绝对值，不该随站点或话题缩放。实测带与不带这两项，评分没有实质差别 |
| 模型返回的分值越界时判为非法结果，不夹取 | 夹取会把一次失败的调用伪装成有效结论 |
| 失败分成"内容不足"与"服务不可用" | 前者要用户换页面，后者要用户稍后重试；提示、状态码与日志级别都不同 |
| "读不出来"是一等结果，不折算成分数 | 只有零散附和或导航文字的页面曾经拿到 0 分、置信度接近 1.0——用户读到的是"这里很平和"，实际含义是"读不出来" |
| 后端给等级代码与失败原因代码，中文措辞留给扩展 | 措辞会反复打磨，不该进契约 |
| 评分口径集中在一个提示词类里 | 换模型或调口径只动一处 |
| 评测基线五段各对应一档，默认不进 CI | 原来只有三段，"争论明显"与"骂战激烈"没有基线。CI 没有模型密钥，只在改提示词或换模型时手动跑。新增的两段是自造的——真实评论属于别人，不适合固化进仓库；钉区间时顺带看清了档位之间差的是什么：不是话题多敏感，而是有没有开始针对人 |
| 校准过一次，口径与分档都不动 | 5 段真实讨论各跑 3 次，档位分得开、抖动远小于档位宽度（数据见"记下来的数据"）。稳定本身是设计使然：模型侧 `temperature = 0`，剩下的是服务端的批处理差异。改提示词没有数据支持，所以不改 |

### 扩展：骨架

| 做法 | 理由 |
| --- | --- |
| 点击工具栏时才注入内容脚本，不声明常驻脚本 | 常驻脚本在每个页面都会跑，与"仅在用户主动请求时读取页面"相抵；权限因此只需 `activeTab` 与 `scripting`。后来加了按网站授权，仍是"看过哪一页才读哪一页"，只是把权限换成了逐站申请 |
| 请求交给后台 Service Worker 发出 | 内容脚本受页面 CORS 限制，后台不受 |
| 浮窗渲染收在一个文件里，其余文件与 UI 无关 | 将来要换 UI 技术时只替换这一层 |
| 后台、内容脚本与授权页各构建一趟 | MV3 的内容脚本不是模块，产物里不能出现 `import`，而 Vite 的多入口模式在 IIFE 格式下不可用；授权页是普通扩展页面，按模块打包即可 |
| 单测只覆盖输入输出都是纯数据的那部分，依赖真实渲染的继续靠浏览器实测 | shadow root、懒加载、`checkVisibility` 在测试环境里要么跑不起来、要么只是在测一个假的渲染层。CI 里加了 `npm run test` |
| 重复注入时复用宿主元素、换上新监听器 | 工具栏每点一次注入一次。**"宿主元素在不在"不等于"当前上下文里有人监听"**：扩展重新加载后，页面里留着上一版的宿主元素，而旧监听器已随旧上下文失效——曾据此提前退出，结果浮窗彻底打不开，只能刷新页面 |
| 关闭浮窗要连"还在跑的那一轮"一起作废 | 分析要等几秒，用户可能在这期间关掉浮窗或再点一次图标。光清 DOM 不够：等回来的代码还在往同一个影子根里画，浮窗就自己回来了。现在每轮分析发一个凭据，收工就清空，对不上不再往下画；同一类收尾还有两处——渲染层关闭时要忘掉手里的视图（否则授权一变的重绘会画回来）、新脚本接手时要让上一份停手（否则它还在轮询）。凭据方法声明成可选，是实测出来的：扩展升级后页面里登记的上一版对象没有它，直接调会让 `start()` 整个中断 |

### 扩展：页面正文提取

| 做法 | 理由 |
| --- | --- |
| 逐节点遍历并下钻 shadow root，不读 `body.innerText` | 评论正文常渲染在 shadow root 内，读 body 只能拿到页面框架 |
| 只把"渲染中"的元素算进正文，离屏元素照样算 | 判据是 `checkVisibility()`，它不把"在屏幕外"当不可见（实测视口下方 5000px 仍返回 true）。这是"滚动不改变被分析那一段"的根基；唯一的例外是虚拟列表，离屏节点直接从 DOM 移除 |
| "未就绪"与"读到空内容"分开判断 | 页面刚打开时讨论容器可能还没挂载，此时若回退整页，会把导航与推荐位当成讨论正文 |
| 站点差异集中在"站点期望表 + 通用回退"一处 | 站点表给出承载讨论的容器，其余站点走通用回退。第二个站点（知乎）落地后看清楚了：差异只有"内容区在不在影子根里""要不要等它渲染""一条内容叫什么"，**没有需要抽的接口** |
| 站点表按容器找，不按页面类型找 | 页面类型列不完（同一个视频站就有首页、搜索、直播、会员购、热榜、专栏），补不全还会随改版失效；而"容器在不在"只有两种结果，正好对应"读到了"与"没读到"。知乎首页、热榜、专栏页与单回答页都没有那个容器，于是与 B 站首页、会员购一样落回"没读到"——没有站点表时，通用回退会把首页那两千多字的编辑器占位当成讨论送去分析 |
| 知乎的讨论是回答，不是评论 | 知乎的评论要点开才加载，页面里根本没有（实测问题页上只有"20 条评论"这个按钮）；问题页上互相辩的就是那些回答。零回答的问题页顺带验了：容器压根不渲染，不会把空态文案当成讨论 |
| 微博只接移动站 | 桌面站的评论装在虚拟列表里，DOM 只留视口附近的 2–9 条，滚动时整批换掉——讨论没变，眼前这段却换了人，会撞上"讨论换了一批"。移动站相反：`.comment-content` 初次渲染约二十条，往下滚只追加不回收。代价：桌面浏览器打开移动站首页是"暂无数据"，入口主要靠分享与外链 |
| 窗口摊在整段上取，不从头切一刀 | 只取开头会把结论绑在排在最前面的那批上：反转刚发生时新声音在开头还很稀疏，报出来的是旧气氛。现在整段摊成五处并列窗口（首贴开头、尾贴结尾、中间等距），各两千字。上一版只取开头时，面板上的条数会冻在一个由字数决定的随机值上，用户据此就能反推出"只取一万字"——这也是改掉它的原因之一 |
| 窗口按行切，不按字符切 | 按字符切会让最后一行只剩半句，后端再按字符硬切一次更糟——切在句子中间对模型是垃圾输入。现在放不下下一行就提前收尾，最后一段从结尾往回取（否则"贴结尾"是句空话）。实测 12899 字的页面送出 9845 字，每一行都是完整的原文行 |
| 条数报"窗口覆盖到几条"，名词跟站点走 | 报出去的必须是结论真正覆盖到的那几条：知乎的问题页有几百个回答，一万字摊下来只是其中几条。所以数的是"哪几条有一行进了窗口"，名词由站点给——B 站与微博是评论，知乎是回答；统一说"评论"在知乎上是错话，说"内容"等于什么都没说。没适配的站点不报条数：通用回退取到的是 `main` 或整页，"一条内容"在那里无从定义。顺带记一笔：微博没有跨微博的评论，评论挂在单条微博下，跨微博的往来是转发链，我们没读 |
| 界面文字按"行的形态"丢，不按站点结构丢 | 评论列表里混着页面自己的控件文字：时间、"共 59 条回复，点击查看"、孤立标点、"回复"。两份真实样本实测各占 31% 与 32% 的字数，相对时间还会随时间变，给"有没有变化"的比对添噪声。"时间戳长什么样"是通用的，"哪个站点的哪个节点"不是。用户名不在此列——它和"同感"这类短回复长得一样，通用规则分不开 |
| 知乎不动行形态过滤 | 与上一条相反的一份样本：知乎是长文答案，页面自己的文字（作者名、徽章、"N 人赞同了该回答"）只占容器字数的 1.1%，没什么可吃的，就不加站点专用规则 |
| 只取文本，不解析单条评论、用户名、点赞、楼层 | 逐条解析会把最容易变的 DOM 结构写进采集核心，而分析并不需要这些字段 |
| 不调用站点接口，不做签名与逆向 | 签名算法会变、要处理风控，而且它站点专有，换个站点等于重做 |

### 扩展：触发加载与等待

| 做法 | 理由 |
| --- | --- |
| 触发懒加载用"无感搬运" | 给容器加 `position: relative; top` 与 `opacity: 0`，只在视觉上把它挪进视口：评论要进视口才加载，而滚动必然移动用户页面，相对定位不参与布局，用户察觉不到。用相对定位而不用 `transform`，是因为自定义元素默认是 inline，`transform` 对 inline 无效、得先改 `display`，那会引起重排 |
| 只在容器不在视口内时才搬 | 容器已在视口里说明页面自己在加载，此时透明化等于把用户正在看的内容藏起来 |
| 无感加载失败时退回真实滚动，且由用户点按钮触发 | 位移必须由用户换来 |
| 面板显示中间态"正在读评论区…" | 搬运期间页面没有任何变化，缺少中间态会让用户以为点击没反应 |
| 讨论文本优先只取评论区，评论区不够大才退回整页 | 讨论是评论之间的事，而 `main`／`article` 里往往先是楼主正文，长正文会把窗口占满；取评论区也顺带跳过了列表头部的计数与排序控件。够大（≥2000 字）才算数：还没加载出来时容器里可能只有"评论"两个字，那时退回整页，有内容的判断总比没有强。实测一份"长正文 + 类名评论区"的页面，送出的样本里没有正文、只有评论 |
| 停止条件是连着三次快照（间隔 500ms）一致 | 一读到内容就停，样本量会随加载进度浮动，同一页面的分数失去可比性；快照次数从两次加到三次，是因为评论分批到达、中间有间隙，只隔一次容易在间隙里"以为读完了"。**原来还附带"样本 ≥2000 字"**，那半条参与的是"能否提前结束等待"，于是样本本来就少的页面只能白等满 8 秒——实测一份 603 字的页面，用户看着"正在读评论区…"等了 8.5 秒，那 8.5 秒里一个字都没再多；拿掉之后同一页面 2.4 秒。那一档字数现在只管"评论区够不够大、值不值得优先于整页" |
| 页面现成有多少就送多少，不因为不足 2000 字而空等 | 2000 字管的是"要不要继续等"，不是"够不够格送"；判断内容够不够是后端的事，它会回 `insufficientContent`。曾经想改成"内容少时先等一会再送"，实测否掉了：B 站首批约 17 条评论、1886 字，带进视口再等 4 秒仍是 1886 字——更多评论只有真实滚动才会追加，而那个动作按约定留给用户 |
| 采集有 8 秒总上限，超时就用已有内容 | 任何路径都不允许无限等待 |
| 等讨论容器的时间从 8 秒收到 1.5 秒 | 8 秒是整个加载预算，而容器在页面骨架里、加载完成时就已存在（实测视频页与番剧页都是）。给容器留整个预算，只会让读不到内容的页面白等满 8 秒——那种页面恰恰最多。这不是判断页面类型，是按实测给等待划一条止损线 |
| 没读到内容时只说没读到，不判断页面类型 | 原来的文案预设了"滚一下就能解决"，而首页、搜索、动态这些页面根本没有讨论区：用户按一次按钮，我们滚一趟、等 8 秒，最后还是同一句话。中途想过按页面类型分开说（判据用站点表里已有的容器），但页面类型列不完。最后只回答"读到了没有"，要不要再试交给用户——他就在那一页上；按钮也因此从"好，去读评论区"改成"好，试一下" |
| 授权站点上自动打开，只有读到内容才出现 | 这条规则不需要知道"哪一页该有讨论区"：拿提取结果说话。以前是进站就画浮窗，于是首页、搜索这些页面会弹出一块"评论还没加载出来"，可用户并没有要求过什么；现在连"正在读评论区"也不闪——加载态是给点了图标的人看的 |

### 扩展：分析链路

| 做法 | 理由 |
| --- | --- |
| 响应体在扩展侧过一道结构校验 | 后端是外部系统，返回结构不受编译期类型约束；缺字段或出现陌生的等级代码时，面板会渲染出 undefined 或空白 |
| 一次分析的结论缓存在会话存储里，键取内容哈希 | 钱和等待都在模型那一侧，而"自动打开"让同一段内容被反复送：每进一次站、每刷一次页面都是一次调用。存 `storage.session` 而不是内存，是因为 Service Worker 会被回收；也不是 `local`，那样会攒出一份越积越旧、来路不明的结论。键取哈希，会话存储里就不必再留一份讨论正文。只记确定性的结论（成功、"内容太少"），暂时性失败不记——一次后端抽风不该让这个页面在整场会话里都不再尝试 |
| `host_permissions` 先只声明本机后端地址 | 部署地址确定之前不扩大权限范围 |
| "服务不可用"与"网络不通"对用户合并成同一句 | 两者对用户是同一件事——过会儿再试；让他去分辨一个自己无能为力的差异没有意义。日志里仍分得清 |
| 置信度低时只加一句"这里的内容不太好判断" | 用户不需要 0.85 这样的数字，只需要知道这次判断不太牢靠 |
| 改动 manifest 或后台脚本后必须重新加载扩展 | 这两样只在扩展加载时更新，而注入的内容脚本是按文件取的 |

### 扩展：浮窗交互

| 做法 | 理由 |
| --- | --- |
| 位置与折叠状态放在渲染层的模块状态里，每次渲染再套回元素 | 面板每次状态变化都会整体重建，位置不能跟着丢 |
| 只有标题栏可拖，圆片整块可拖；指针移动超过 4 像素才算拖动 | 正文里要能选中文字、点按钮，圆片没有别的内容；同一套指针处理要同时支持"拖圆片"和"点圆片展开" |
| 拖动时与视口变化后都把位置夹在可见范围内 | 否则浮窗会被拖出屏幕，只剩"再点一次图标"这种很隐蔽的恢复方式 |
| 浮窗自带 `position: fixed` 与最高 `z-index` | 宿主元素排在文档流末尾：少了定位圆片会落到页面底部，少了 `z-index` 会被站点浮层盖住、连拖都拖不动 |
| 八向都能拖，且拖哪条边对面那条不动 | 拉窗口这件事八个方向都得有；若整个面板跟着动，手感会变成"在搬东西"而不是"在改尺寸" |
| 内容区独立滚动，标题栏固定 | 面板能被拖矮之后，内容必须能在里面滚，否则会把标题栏顶出去 |
| 高度默认由内容撑，用户拖过之后才固定 | 内容长短不该由我们猜 |
| 宽高上限跟着屏幕走，不设固定数值 | 上限应当表现为"到头了"，而不是"撞上一个数字"（曾把宽度上限写成 460，实测很容易撞到） |
| 宽度下限 116px、高度下限 49px | 下限只留控件自身的尺寸：再小就有按钮被挤出窗口，用户丢的不是读数，而是"收起"这条回程。这个数改过四次（240 → 80 → 72 → 94 → 116）：可读性那个初值是替用户做判断，后来按"用户能判断、能撤销的事不该由产品锁死"下调；后两次上调都因为标题栏多了一个控件 |
| 窗口压到极小时内容被裁掉，而不是溢出边框 | 极窄极矮时子元素总要占地方；宁可裁掉，也不要让文字和按钮飘到圆角外面 |
| 窗口很窄时先牺牲标题，几个按钮始终留得住 | 标题截断只是丢了个名字，按钮被挤出去就真的关不掉了（实测最小尺寸 116×49 下四个按钮仍完整可点） |
| 浮窗的落点与形态记在会话存储里，尺寸不记 | 落点是"我想放这儿"、形态是"我想让它这样收着"，都是用户明确做出的选择，记下来不必每页重拖重收（浏览器一关回默认）；尺寸跟着内容看，每次回默认更省事，也不会出现"上次拖小到看不见"这种需要额外回程的状态。只存 `storage.session`，因此不需要"恢复默认"——注意会话存储默认不对内容脚本开放，后台要显式放开 |
| 变宽越过右边缘时把面板整体左移，而不是限制宽度 | 面板默认停在右上角，限制宽度会让它连默认宽度都回不去 |
| 缩放热区平时透明，指针压上去才显出一条边 | 它们不该破坏外观，也不能让人猜：原来把显隐挂在面板的 `pointerenter` 上、手柄又是透明的，等于什么都没显。四边 10px、四角 16px——6px 抓不住，再宽就吃掉面板内部的可用面积 |
| 浮窗挂在影子根里 | 页面自己的样式再也渗不进来（继承类的、伪元素类的原先都会影响浮窗；实测站点设了 `letter-spacing: 3px` 时浮窗仍是 `normal`），顺带给了样式表一个落脚处——滚动条、文字选中色这类内联写法表达不了的东西才写得进去。代价：定位与夹取不能再从宿主元素的子节点里翻，改成记住当前画出来的元素 |
| 面板与圆片共用同一套表面：深色毛玻璃、带描边 | 收起前后应当是同一个东西；半透明必须配描边与模糊，否则在浅色页面上会糊成一片。压在毛玻璃上的浅色文字，透明度不低于 0.8——毛玻璃的底色跟着页面走，0.6 会把 13px 字的对比度压到 4 左右 |
| 圆片保持中性，不按等级上色 | 客户端上的彩色块容易被读成游戏化的装饰，与工具的气质不合 |
| 分数与等级分成两级：数字 26px、等级 13px 次要标签 | 原先两者同处一行、字号只差两级，扫一眼分不出哪个是结论 |
| 标题栏加一个"重新分析"图标 | 原来只有结果过期时才给重算按钮，想立刻重读只能再点一次工具栏图标——那是个藏起来的动作 |
| 留白只留两档：行与行 6px、区域与区域 12px，标题栏下例外给 16px | 正文第一行是 26px 的数字，方块大、行高紧，同样 12px 看着像贴着标题；设置区与正文之间再加一条细线（用面板描边那档白），比单纯留白更省地方、也更好认 |

### 扩展：结果过期检测

| 做法 | 理由 |
| --- | --- |
| 比对范围就是送去分析的那一段（窗口在提取时切好） | 后端那道截断只是兜底。若比对整页，用户只是往下翻、让窗口之外加载出更多评论，也会被提示"内容变了"，而分数本来就没覆盖那些内容 |
| 基线取刚送去分析的那段文本，而不是分析返回后重读页面 | 分析与返回之间页面可能又加载了内容，那些内容并没有被这次分析覆盖，不该被当成已分析 |
| 比对按行集合做，只看新增行；"变多"与"整段被换掉"分开判 | 评论逐条出现，新出现的行才说明被分析的那段变了。原来两者走同一条判断，于是换排序之后旧分数还留在浮窗上——同一页里被分析的那批整段换掉，与换页是同一件事：一条都不在眼前了。现在：变多 → 保留分数 + 提示重算；被分析那段的行消失过半（换排序、换筛选）→ 撤掉分数。判据用"消失"而不是"新增"：换排序后新来的一批当然也是新的，但说明"换了"的是原先那批不见了；评论自然增长时旧行都在，它恒为 false。实测同一视频切排序（两份样本行重合度 17%）后 13 秒内给出替换提示，人工追加 15 条评论仍走"变多"分支 |
| 阈值：新增行 ≥ 10 条，或新增行占当前行的 20% | 绝对值管大页面，比例管小页面。两个数都是初值，要用真实使用校准 |
| 只比够长的行（≥ 8 字） | 相对时间与点赞数这类短行每次刷新都可能变，攒几条就够凑到阈值。代价：短回复不参与比对——它们本来也构不成"变化大"。实测：20 条时间戳同时变不触发，另添 10 条长篇评论才触发 |
| 换页判断只比 `pathname` | 站点常在 query 里追加跟踪参数（B 站的 `vd_source`、`spm_id_from`），比完整地址会误判成换页 |
| 比对周期 10 秒，且只在页面可见时执行 | B 站一次加载 20 条评论，更频繁没有意义；页面不可见时用户在别的标签页上 |
| 放弃"先看廉价信号、再比行集合"的两段式 | 廉价信号（容器子元素数）会漏掉"回复被展开"这类变化，而完整比对本来就要遍历一次 DOM，省不掉 |

### 扩展：进入网站时自动打开

| 做法 | 理由 |
| --- | --- |
| 按网站逐个申请 host 权限，也不申请 `tabs` | 安装时的"读取您在所有网站上的数据"会吓到人，也与"仅在需要时读页面"的立场相抵；逐站申请时，那句权限提示就只讲那一个站点。不申请 `tabs`：看不见地址就注入不了，权限本身就是功能的开关，不必再写一层"这个站点允不允许" |
| 请求授权落在扩展页面上，标题栏那个设置图标只负责开合 | 请求 host 权限必须在用户手势里发起，而内容脚本里没有 `chrome.permissions`，从后台的消息处理器里调也不算手势——Chrome 只认扩展页面上的那次点击。这不是设计选择，是平台规矩 |
| 授权界面嵌在浮窗里，不是另开窗口 | 嵌进来之后"再点一次收起"是自然的；独立窗口每点一次就多一个，用户得自己收拾 |
| 嵌入页自报高度，两端都认来源 | 跨源文档之间量不到对方高度，只能由嵌入页报回来。嵌入页发时指名目标来源，面板收时校验来源、窗口与消息形状——实测从页面本身伪造同样内容不会生效 |
| 嵌不进来就退到独立窗口 | 站点可以用 CSP 静默挡掉嵌进来的扩展页面。等不到高度就把设置区换成"设置区加载失败"加一个按钮：宁可多一次跳转，也不要用户对着空白猜 |
| 失败文案只说哪一块没成，不猜原因 | 早先写成"这个网站不允许读空气在这里显示设置"，把原因归到站点上——用户更信站点，这句读起来像是我们被站点拒了；何况失败未必是站点的原因，我们本来就不知道 |
| 文案按"标准叫法 + 只说管什么"来写 | "收起"不写"最小化"（那是收进任务栏再取回），也不写"折叠"（界面里多指文本区块），它还和圆片上的"展开读空气"配成一对；设置区的标签要说出被打开的是什么（"进入网站时自动打开读空气"）、并限定范围（"当前网站"）。"开启后……""关掉即可"都在重复标签已经说清的事，不写 |
| 状态用开关，不用"开启/关闭"两个按钮 | 动词按钮要求用户把动词反过来读才知道当前状态；开关蓝开灰关，状态自己说话。列表页保留"关闭"按钮——那里做的是"把这个站点移除"，不是翻一个布尔值 |
| 设置图标兼作状态：本站已开启时染成强调色，设置区展开时带一层底色 | 原来"已在本站自动打开"是一行字，去掉后状态就没地方说了；染色后对比度约 7:1，扫一眼就能看出这个站是不是开着 |
| 图标用两根滑杆，不用齿轮 | 16px 下画齿轮会糊成一团；滑杆四条线段画得准，也更像"这里是一小块设置" |
| 授权页的底色一律不透明 | 次按钮与开关轨道原来是半透明白，衬在渐变上颜色会随位置变，对比度静态分析也算不准；换成同色相的不透明值，观感几乎一样，读数确定 |
| 触发点选"页面加载完成"，不理会站内换页 | 站内换页已由浮窗自己的"页面换过了"兜着，这里再插一脚就是两套逻辑做同一件事 |
| 授权页不自己关 | 开关都长在这一页上，一关就断了来回改的路径，也让没看清的人以为没办成 |
| 兜底窗口沿用浮窗那一套外观，落在屏幕中上位置 | 它是同一个产品在说话，不该长得像另一件东西（最初用的是浅色网页样式）；不指定位置时由系统决定，实测跑到屏幕左下角，既不像一次提问，也离用户在看的地方远 |
| 授权名单记在 storage 里，而不是每次去读已授权的 host 权限 | 内容脚本要拿它决定设置图标染不染色，而它读不到 `chrome.permissions`；storage 的变更通知还顺带解决了"授权完成后图标要跟着变" |
| 关闭的两步收在 `shared/auto-open` 里，开启拆在页面里 | 关掉一个站点 = 名单去掉 + 权限还回，两步分开写迟早会漏一步；"开启"做不到合并——请求权限必须在用户手势里发起 |
| 设置页暂时不做"恢复默认设置" | 它服务的问题还不存在：窗口尺寸并不记忆，授权也能逐个关掉 |
| 隐私告知：第一次真的把文字发出去时说一次，设置里另留一个入口 | 两件事各管一半——提示管"第一次发生时知情"，入口管"事后可查证"；入口藏在设置图标后面，替不了提示。说在"发出请求"那一刻，不是"拿到结论"：文字离开浏览器发生在请求发出时，与模型答没答出来无关（第一次撞上"内容太少"时文字照样到了服务器，此时不说就得等到某次成功，告知晚于事实就不叫告知）。说过记在 `storage.local`（记 session 会每开一次浏览器就说一遍），且是显示的那一刻就记下。不写"该声明只显示一次"——它对用户没有决策价值，一句话的版面该留给"发了什么、留不留" |
| 隐私文案的几条取舍 | 措辞集中在 `shared/privacy`，免得一处改了另一处没改；不点名服务商（换个供应商就要改文案）；"外部"改"第三方"，与"自己的服务器"对照；原稿三句只讲我们怎样、没有回程，补一句"不想自动发送就在设置里关掉"；"服务器不保存这些文字"是读过代码确认的，所以可以照实写 |

## 二、过程中总结出来的判断依据

这部分不描述项目现在长什么样，只回答"这类事往哪边定"。

**强制只用在不可逆的地方。**
用户自己能判断、能撤销的事，不由产品替他锁死：窗口能拖到多小、要不要自动打开、要不要重算，都是他的事。产品只守住真正越不过去的那条线——窗口小到控件自己装不下就不能再小，因为那时他连"收起"都点不到，丢的不是读数，是回程。

**给了控制权就要给回程。**
只给开关不给撤销，不是授权，是甩锅。每个"打开"旁边都该有"关掉"。

**用户没要求的动作不做。**
不替他滚页面、不替他重算、不替他发请求：这些动作要么动了他的页面，要么花了他的钱，而收益只是"也许能多看一眼"。要动，就由他点一下换来。

**只描述事实，不替用户解释原因。**
我们说不准的事就别猜：没读到内容时不说"这一页没有讨论区"，也不说"评论区还没加载"；设置区加载失败时不说是站点挡的；按钮不预设"滚过去就有"。解释得越具体，越可能替用户下一个我们并不知道的结论。

**数值从实测来，不从感觉来。**
等待门槛、容器等待、窗口形状、条数口径，几处初值都被实测推翻过（2000 字门槛让 603 字的页面白等 8.5 秒；窗口只取开头让"取到哪一批"决定结论）。定数值之前先问"拿什么量它"。

**能让平台约束替我们做判断的，就不自己再写一层。**
不申请 `tabs` 权限——看不见地址就注入不了，于是"这个站点允不允许"不必再判断一次。

## 三、想法区

**这一部分不受文档规范约束：想到什么写什么，包括可能不靠谱的。写在这里不代表已经决定，回头翻的时候按当时的情况重新判断。**

### 想过，还没定

- **桌面吉祥物**：用颜色表达情绪这件事，更适合交给一个有形象的角色（QQ 宠物、瑞星小狮子那种路子：心情好偏蓝绿，生气就红温），而不是撒在控件上的色块。MVP 不做，先记着。

### 记下来的数据

- **评测基线与校准**：五段样本各跑两次核验——平和 5/5、争论 45/58、对立 78/78、骂战 88/88，附和那段两次都回 422「内容不足以分析」。另用 5 段真实 B 站讨论各跑 3 次校准：5 / 18 / 38 / 42 / 72，档位依次平和、平和、还算理性、争论明显、对立明显；四段三次完全一致，只有最平和那段出现过 12/18/22。两处要留意："对立"那段贴着自己档位的上沿（78，上界 80），"争论"那段两次差 13 分（45 与 58）——改口径时它们最可能先变红。模型单次判断（5–10k 字输入）0.6–1.3 秒。
- **等待与响应**：点图标到浮窗出现几乎实时；内容已渲染的页面不到 1 秒出结果；需要搬运评论区的页面约 2.4 秒（等稳定 1.5 秒 + 模型约 1 秒）；改掉字数门槛之前同一页面要等 8.5 秒。分批到达的页面（每 300ms 一条）：最后一条之后约 1.5 秒开算，样本含最后一条。用户的等待几乎全部来自模型判断。
- **窗口与"有新变化"的实测**：12899 字 / 386 行的知乎问题页，送出的窗口 9845 字 / 296 行，每行完整、首尾都在。稳定性（把讨论缩短后再取一次）：缩到 95% / 80% / 50% 时，旧窗口仍有 90.6% / 81.3% / 74.1% 的行留在新窗口里（"整段被替换"的阈值是消失 50%）。触发门槛：短 0.5% → 新增 4 行不触发，短 2% → 7 行不触发，短 5% → 37 行触发——也就是要长到 3–4%（几百字）才会提示一次。
- **换排序的实测（两段视频）**：彩礼那条（5556 字）最热与最新两份样本行重合度 17%，分数 38 与 42——两批氛围相近，**不能据此说"分数对抽到哪一批不敏感"**；华为小米那条（最热 7957 字、最新 14286 字）最热 42、最新 62，差 20 分跨一档——最新排序的前排是近期短促的对骂，最热的前排是高赞的长篇数据对比。**"取到哪一批"确实能改变结论。**
- **截断代表的四次尝试**：前三次都问不出什么（同一视频的前中后窗口、换排序的两批、跨八个月的两个 7000 字窗口）——样本在"氛围"这个维度上是均匀的。第四次按"塌房明星"找（23705 字，评论跨 2022 年塌房当时到 2026 年）：三千字窗口给 42 与 62，说明**样本内部确实不均匀**；一万字窗口前后段都是 62。与直觉相反：最激烈的是塌房当时的 2022 年，四年后的围观反而平静。

### 想过，目前不做

- **逐条评论解析、按条数计数（20/50 那种）、文本去重**：去重会削掉"一大片同感"这类本该计入的样本。
- **MutationObserver**：新建的 shadow root 不会触发宿主上的 observer，"发现新 shadow root"本身还得轮询——除非去改页面主世界的 `attachShadow`。
- **`scrollIntoView` 触发 + 采集后恢复滚动位置**：被无感搬运取代，连"恢复位置"这个需求一起消失。
- **进入页面就自动采集或预热**：与"仅在用户主动请求时才把内容发往服务器"冲突，而且自动触发必然移动页面。
- **固定条数上限**：停止条件已经是"够样本且稳定"，条数上限是同一意图的另一种表达，不必并存。
- **静默加载更多页**：容量这一环已经接住（窗口摊在整段上，读得越多越有代表性），不做是因为**不愿动用户的页面**——目前允许的位移只有用户自己点按钮换来的那一次。
- **自动重算**：体验最好，但要额外授权（点过一次分析不等于授权持续把页面内容发往服务器）、要控制成本。仍只做提示——重算要花钱，而"要不要多看一眼"用户一眼能判断。
- **采集器接口 + 每站一个实现类**：知乎落地后看过了，不抽——站点之间的差异只有"多一个影子根内层选择器""一条内容叫什么"这些数据，站点表多几行就装下了。
- **通用爬虫框架、事件总线、插件系统**。

### 还没验证

- **真实点击工具栏**：受扩展权限模型限制，需要用户手势，我模拟不了。
- **兜底滚动路径**：缺一个能让无感加载失败的真实页面。如果各站点都支持无感，这条路径可能变成死代码。
- **加载很慢 / 评论区始终不出现 / 评论数量不足**这三种情形。
- **SPA 切换视频**。
