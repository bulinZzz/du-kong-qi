# 读空气 开发记录

这是一份开发过程记录，不是设计说明。

它与文档规范有意冲突：按 [AGENTS.md](../AGENTS.md) §8，文档只描述最终状态，不保留历史方案与修改过程；而本文恰恰要留下演进——比如"停止条件为什么从 2000 字改成了另一个值"，这类信息别处没有地方放，忘掉之后容易被重新提议。

因此约定：

- **当前的设计与结构以 [03-技术设计.md](03-技术设计.md) 和代码为准**，本文可能与其不一致；
- 做法变化时补一行说明变化与原因，不改写原记录；
- 只留"为什么这么定"与"什么证据让我改"。取值、尺寸、颜色、间隔这类能从代码直接读出的东西，一律不记。

读它的时候留意这个区别：写"因此"的地方是判断，还在写"现在"的地方只是当时的实现。做法与理由在第一部分，可迁移的工程判断在第二部分，量过的数据与尚未验证的事各自独立成节，想法在最后。

## 一、已开发

### 后端：空气分析接口

| 做法 | 理由 |
| --- | --- |
| 公开契约只收页面文本，不收标题与地址 | 指标描述的是讨论自身的对抗性，是绝对值，不该随站点或话题缩放。实测带与不带这两项，评分没有实质差别 |
| 模型返回的分值越界时判为非法结果，不夹取 | 夹取会把一次失败的调用伪装成有效结论 |
| 失败分成"内容不足"与"服务不可用" | 前者要用户换页面，后者要用户稍后重试；提示、状态码与日志级别都不同 |
| "读不出来"是一等结果，不折算成分数 | 只有零散附和或导航文字的页面曾经拿到 0 分、置信度接近 1.0——用户读到的是"这里很平和"，实际含义是"读不出来" |
| 后端给等级代码与失败原因代码，中文措辞留给扩展 | 措辞会反复打磨，不该进契约 |
| 评分口径集中在一个提示词类里 | 换模型或调口径只动一处 |
| 评测基线五段各对应一档，默认不进 CI | 原来只有三段，"争论明显"与"骂战激烈"没有基线。CI 没有模型密钥，只在改提示词或换模型时手动跑。新增的两段是自造的——真实评论属于别人，不适合固化进仓库；钉区间时顺带看清了档位之间差的是什么：不是话题多敏感，而是有没有开始针对人 |
| 校准过一次，口径与分档都不动 | 5 段真实讨论各跑 3 次，档位分得开、抖动远小于档位宽度（数据见"记下来的数据"）。稳定本身是设计使然：模型侧 `temperature = 0`，剩下的是服务端的批处理差异。改提示词没有数据支持，所以不改 |

### 扩展：骨架

| 做法 | 理由 |
| --- | --- |
| 点击工具栏时才注入内容脚本，不声明常驻脚本 | 常驻脚本在每个页面都会跑，与"仅在用户主动请求时读取页面"相抵；权限因此只需 `activeTab` 与 `scripting`。后来加了按网站授权，仍是"看过哪一页才读哪一页"，只是把权限换成了逐站申请 |
| 请求交给后台 Service Worker 发出 | 内容脚本受页面 CORS 限制，后台不受 |
| 浮窗渲染收在一个文件里，其余文件与 UI 无关 | 将来要换 UI 技术时只替换这一层 |
| 后台、内容脚本与授权页各构建一趟 | MV3 的内容脚本不是模块，产物里不能出现 `import`，而 Vite 的多入口模式在 IIFE 格式下不可用；授权页是普通扩展页面，按模块打包即可 |
| 单测只覆盖输入输出都是纯数据的那部分，依赖真实渲染的继续靠浏览器实测 | shadow root、懒加载、`checkVisibility` 在测试环境里要么跑不起来、要么只是在测一个假的渲染层。CI 里加了 `npm run test` |
| 重复注入时复用宿主元素、换上新监听器 | 工具栏每点一次注入一次。**"宿主元素在不在"不等于"当前上下文里有人监听"**：扩展重新加载后，页面里留着上一版的宿主元素，而旧监听器已随旧上下文失效——曾据此提前退出，结果浮窗彻底打不开，只能刷新页面 |
| 关闭浮窗要连"还在跑的那一轮"一起作废 | 分析要等几秒，用户可能在这期间关掉浮窗或再点一次图标。光清 DOM 不够：等回来的代码还在往同一个影子根里画，浮窗就自己回来了。现在每轮分析发一个凭据，收工就清空，对不上不再往下画。这类异步收尾不止一处——关闭时要忘掉手里的视图，新脚本接手时要让上一份停手——所以凭据式作废要当成一条通用做法，而不是就地打一个补丁。凭据方法声明成可选是实测逼出来的：扩展升级后页面里登记的上一版对象没有它，直接调会让整段逻辑中断 |

### 扩展：页面正文提取

| 做法 | 理由 |
| --- | --- |
| 逐节点遍历并下钻 shadow root，不读 `body.innerText` | 评论正文常渲染在 shadow root 内，读 body 只能拿到页面框架 |
| 只把"渲染中"的元素算进正文，离屏元素照样算 | 判据是 `checkVisibility()`，它不把"在屏幕外"当不可见（实测视口下方 5000px 仍返回 true）。这是"滚动不改变被分析那一段"的根基；唯一的例外是虚拟列表，离屏节点直接从 DOM 移除 |
| "未就绪"与"读到空内容"分开判断 | 页面刚打开时讨论容器可能还没挂载，此时若回退整页，会把导航与推荐位当成讨论正文 |
| 站点差异集中在"站点期望表 + 通用回退"一处 | 站点表给出承载讨论的容器，其余站点走通用回退。第二个站点（知乎）落地后看清楚了：差异只有"内容区在不在影子根里""要不要等它渲染""一条内容叫什么"，**没有需要抽的接口** |
| 站点表按容器找，不按页面类型找 | 页面类型列不完（同一个视频站就有首页、搜索、直播、会员购、热榜、专栏），补不全还会随改版失效；而"容器在不在"只有两种结果，正好对应"读到了"与"没读到"。知乎首页、热榜、专栏页与单回答页都没有那个容器，于是与 B 站首页、会员购一样落回"没读到"——没有站点表时，通用回退会把首页那两千多字的编辑器占位当成讨论送去分析 |
| 知乎的讨论是回答，不是评论 | 知乎的评论要点开才加载，页面里根本没有（实测问题页上只有"20 条评论"这个按钮）；问题页上互相辩的就是那些回答。零回答的问题页顺带验了：容器压根不渲染，不会把空态文案当成讨论 |
| 微博只接移动站 | 桌面站的评论装在虚拟列表里，DOM 只留视口附近的两三条到八九条，滚动时整批换掉——讨论没变，眼前这段却换了人，会撞上"讨论换了一批"。移动站相反：初次渲染约二十条，往下滚只追加不回收。代价：桌面浏览器打开移动站首页是"暂无数据"，入口主要靠分享与外链 |
| 窗口摊在整段上取，不从头切一刀 | 只取开头会把结论绑在排在最前面的那批上：反转刚发生时新声音在开头还很稀疏，报出来的是旧气氛。改成整段摊成若干并列窗口（首贴开头、尾贴结尾、中间等距）。上一版只取开头时，面板上的条数会冻在一个由字数决定的随机值上，用户据此就能反推出"只取一万字"——这也是改掉它的原因之一 |
| 窗口按行切，不按字符切 | 按字符切会让最后一行只剩半句，后端再按字符硬切一次更糟——切在句子中间对模型是垃圾输入。所以放不下下一行就提前收尾，最后一段从结尾往回取（否则"贴结尾"是句空话）。实测送出的每一行都是完整的原文行 |
| 条数报"窗口覆盖到几条"，名词跟站点走 | 报出去的必须是结论真正覆盖到的那几条：知乎的问题页有几百个回答，一个窗口摊下来只是其中几条。所以数的是"哪几条有一行进了窗口"，名词由站点给——B 站与微博是评论，知乎是回答；统一说"评论"在知乎上是错话，说"内容"等于什么都没说。没适配的站点不报条数：通用回退取到的是 `main` 或整页，"一条内容"在那里无从定义。顺带记一笔：微博没有跨微博的评论，评论挂在单条微博下，跨微博的往来是转发链，我们没读 |
| 界面文字按"行的形态"丢，不按站点结构丢 | 评论列表里混着页面自己的控件文字：时间、"共 59 条回复，点击查看"、孤立标点、"回复"。两份真实样本实测各占 31% 与 32% 的字数，相对时间还会随时间变，给"有没有变化"的比对添噪声。"时间戳长什么样"是通用的，"哪个站点的哪个节点"不是。用户名不在此列——它和"同感"这类短回复长得一样，通用规则分不开 |
| 知乎不动行形态过滤 | 与上一条相反的一份样本：知乎是长文答案，页面自己的文字（作者名、徽章、"N 人赞同了该回答"）只占容器字数的 1.1%，没什么可吃的，就不加站点专用规则 |
| 只取文本，不解析单条评论、用户名、点赞、楼层 | 逐条解析会把最容易变的 DOM 结构写进采集核心，而分析并不需要这些字段 |
| 不调用站点接口，不做签名与逆向 | 签名算法会变、要处理风控，而且它站点专有，换个站点等于重做 |

### 扩展：触发加载与等待

| 做法 | 理由 |
| --- | --- |
| 触发懒加载用"无感搬运" | 只在视觉上把容器挪进视口：评论要进视口才加载，而滚动必然移动用户页面，相对定位不参与布局，用户察觉不到。用相对定位而不用 `transform`，是因为自定义元素默认是 inline，`transform` 对 inline 无效、得先改 `display`，那会引起重排 |
| 只在容器不在视口内时才搬 | 容器已在视口里说明页面自己在加载，此时透明化等于把用户正在看的内容藏起来 |
| 无感加载失败时退回真实滚动，且由用户点按钮触发 | 位移必须由用户换来 |
| 面板显示中间态"正在读评论区…" | 搬运期间页面没有任何变化，缺少中间态会让用户以为点击没反应 |
| 讨论文本优先只取评论区，评论区不够大才退回整页 | 讨论是评论之间的事，而 `main`／`article` 里往往先是楼主正文，长正文会把窗口占满；取评论区也顺带跳过了列表头部的计数与排序控件。够大才算数：还没加载出来时容器里可能只有"评论"两个字，那时退回整页，有内容的判断总比没有强。实测一份"长正文 + 类名评论区"的页面，送出的样本里没有正文、只有评论 |
| 停止条件是连着几次快照一致 | 一读到内容就停，样本量会随加载进度浮动，同一页面的分数失去可比性；次数从两次加到三次，是因为评论分批到达、中间有间隙，只隔一次容易在间隙里"以为读完了"。**这个条件原来还附带"样本够长"**，那半条参与的是"能否提前结束等待"，于是样本本来就少的页面只能白等满整个预算——实测一份 603 字的页面，用户看着"正在读评论区…"等了 8.5 秒，那 8.5 秒里一个字都没再多；拿掉之后同一页面 2.4 秒。字数那一档现在只管"评论区够不够大、值不值得优先于整页" |
| 页面现成有多少就送多少，不因为内容少而空等 | 字数门槛管的是"要不要继续等"，不是"够不够格送"；判断内容够不够是后端的事，它会回 `insufficientContent`。曾经想改成"内容少时先等一会再送"，实测否掉了：B 站首批约 17 条评论、1886 字，带进视口再等 4 秒仍是 1886 字——更多评论只有真实滚动才会追加，而那个动作按约定留给用户 |
| 采集有总上限，超时就用已有内容 | 任何路径都不允许无限等待 |
| 等讨论容器单独设一条止损线，不占用整个加载预算 | 容器在页面骨架里、加载完成时就已存在（实测视频页与番剧页都是）。把整个预算都留给它，只会让读不到内容的页面白等满那一整段——而那种页面恰恰最多。这不是判断页面类型，是按实测给等待划线 |
| 没读到内容时只说没读到，不判断页面类型 | 原来的文案预设了"滚一下就能解决"，而首页、搜索、动态这些页面根本没有讨论区：用户按一次按钮，我们滚一趟、等满预算，最后还是同一句话。中途想过按页面类型分开说（判据用站点表里已有的容器），但页面类型列不完。最后只回答"读到了没有"，要不要再试交给用户——他就在那一页上；按钮也因此从"好，去读评论区"改成"好，试一下" |
| 授权站点上自动打开，只有读到内容才出现 | 这条规则不需要知道"哪一页该有讨论区"：拿提取结果说话。以前是进站就画浮窗，于是首页、搜索这些页面会弹出一块"评论还没加载出来"，可用户并没有要求过什么；现在连"正在读评论区"也不闪——加载态是给点了图标的人看的 |

### 扩展：分析链路

| 做法 | 理由 |
| --- | --- |
| 响应体在扩展侧过一道结构校验 | 后端是外部系统，返回结构不受编译期类型约束；缺字段或出现陌生的等级代码时，面板会渲染出 undefined 或空白 |
| 一次分析的结论缓存在会话存储里，键取内容哈希 | 钱和等待都在模型那一侧，而"自动打开"让同一段内容被反复送：每进一次站、每刷一次页面都是一次调用。存 `session` 而不是内存，是因为 Service Worker 会被回收；也不是 `local`，那样会攒出一份越积越旧、来路不明的结论。键取哈希，会话存储里就不必再留一份讨论正文。只记确定性的结论（成功、"内容太少"），暂时性失败不记——一次后端抽风不该让这个页面在整场会话里都不再尝试 |
| `host_permissions` 先只声明本机后端地址 | 部署地址确定之前不扩大权限范围 |
| "服务不可用"与"网络不通"对用户合并成同一句 | 两者对用户是同一件事——过会儿再试；让他去分辨一个自己无能为力的差异没有意义。日志里仍分得清 |
| 置信度低时只加一句"这里的内容不太好判断" | 用户不需要 0.85 这样的数字，只需要知道这次判断不太牢靠 |
| 改动 manifest 或后台脚本后必须重新加载扩展 | 这两样只在扩展加载时更新，而注入的内容脚本是按文件取的 |

### 扩展：浮窗交互

| 做法 | 理由 |
| --- | --- |
| 位置与折叠状态放在渲染层的模块状态里，每次渲染再套回元素 | 面板每次状态变化都会整体重建，位置不能跟着丢 |
| 只有标题栏可拖，圆片整块可拖；指针要移动超过一段距离才算拖动 | 正文里要能选中文字、点按钮，圆片没有别的内容；同一套指针处理要同时支持"拖圆片"和"点圆片展开" |
| 拖动时与视口变化后都把位置夹在可见范围内 | 否则浮窗会被拖出屏幕，只剩"再点一次图标"这种很隐蔽的恢复方式 |
| 浮窗自带固定定位与最高层级 | 宿主元素排在文档流末尾：少了定位圆片会落到页面底部，少了层级会被站点浮层盖住、连拖都拖不动 |
| 八向都能拖，且拖哪条边对面那条不动 | 拉窗口这件事八个方向都得有；若整个面板跟着动，手感会变成"在搬东西"而不是"在改尺寸" |
| 内容区独立滚动，标题栏固定 | 面板能被拖矮之后，内容必须能在里面滚，否则会把标题栏顶出去 |
| 高度默认由内容撑，用户拖过之后才固定 | 内容长短不该由我们猜 |
| 宽高上限跟着屏幕走，不设固定数值 | 上限应当表现为"到头了"，而不是"撞上一个数字"（曾把宽度上限写成固定值，实测很容易撞到） |
| 宽高下限只留控件自身的尺寸 | 再小就有按钮被挤出窗口，用户丢的不是读数，而是"收起"这条回程。这个下限改过四次：可读性那个初值是替用户做判断，后来按"用户能判断、能撤销的事不该由产品锁死"下调；最后两次上调都因为标题栏多了一个控件 |
| 窗口压到极小时内容被裁掉，而不是溢出边框 | 极窄极矮时子元素总要占地方；宁可裁掉，也不要让文字和按钮飘到圆角外面 |
| 窗口很窄时先牺牲标题，几个按钮始终留得住 | 标题截断只是丢了个名字，按钮被挤出去就真的关不掉了（实测最小尺寸下四个按钮仍完整可点） |
| 浮窗的落点与形态记在会话存储里，尺寸不记 | 落点是"我想放这儿"、形态是"我想让它这样收着"，都是用户明确做出的选择，记下来不必每页重拖重收（浏览器一关回默认）；尺寸跟着内容看，每次回默认更省事，也不会出现"上次拖小到看不见"这种需要额外回程的状态。只存会话存储，因此不需要"恢复默认"——注意会话存储默认不对内容脚本开放，后台要显式放开 |
| 变宽越过右边缘时把面板整体左移，而不是限制宽度 | 面板默认停在右上角，限制宽度会让它连默认宽度都回不去 |
| 缩放热区平时透明，指针压上去才显出一条边 | 它们不该破坏外观，也不能让人猜：原来把显隐挂在面板的悬停上、手柄又是透明的，等于什么都没显。热区太薄抓不住，再厚就吃掉面板内部的可用面积 |
| 浮窗挂在影子根里 | 页面自己的样式再也渗不进来（继承类的、伪元素类的原先都会影响浮窗；实测站点设了大字距时浮窗仍不受影响），顺带给了样式表一个落脚处——滚动条、文字选中色这类内联写法表达不了的东西才写得进去。代价：定位与夹取不能再从宿主元素的子节点里翻，改成记住当前画出来的元素 |
| 面板与圆片共用同一套表面：深色毛玻璃、带描边 | 收起前后应当是同一个东西；半透明必须配描边与模糊，否则在浅色页面上会糊成一片。压在毛玻璃上的浅色文字要留够对比度——毛玻璃的底色跟着页面走，稍微调低一点，小字的对比度就会掉到可读线以下 |
| 圆片保持中性，不按等级上色 | 客户端上的彩色块容易被读成游戏化的装饰，与工具的气质不合 |
| 分数与等级分成两级：数字占主位，等级降成次要标签 | 原先两者同处一行、字号只差两级，扫一眼分不出哪个才是结论 |
| 读数旁边写上它叫什么（"火药味"），圆片的悬停与无障碍标签也带上 | 面板里到处是"读空气"（产品名）与档位词（"对立明显"），但两者都不说明这个数字量的是什么：一个孤立的 58，用户既看不出量的是什么、也看不出哪一端才算糟；圆片上只有一个数字，更没有语境。名字还得跟数字连起来读得通——第一版写成"激烈程度"，那是个仪表词，汉语里没有"空气很激烈"这种说法；"火药味"自带程度与方向（"没什么火药味"／"火药味很浓"），数字大就是糟 |
| 标题栏加一个"重新分析"图标 | 原来只有结果过期时才给重算按钮，想立刻重读只能再点一次工具栏图标——那是个藏起来的动作 |
| 留白只留两档，标题栏下那一段例外放宽 | 方块大、行高紧的正文（那个大号数字）用同样的间距看着像贴着标题，所以它下面单独放宽；设置区与正文之间再加一条细线，比单纯留白更省地方、也更好认 |

### 扩展：结果过期检测

| 做法 | 理由 |
| --- | --- |
| 比对范围就是送去分析的那一段（窗口在提取时切好） | 后端那道截断只是兜底。若比对整页，用户只是往下翻、让窗口之外加载出更多评论，也会被提示"内容变了"，而分数本来就没覆盖那些内容 |
| 基线取刚送去分析的那段文本，而不是分析返回后重读页面 | 分析与返回之间页面可能又加载了内容，那些内容并没有被这次分析覆盖，不该被当成已分析 |
| 比对按行集合做，只看新增行；"变多"与"整段被换掉"分开判 | 评论逐条出现，新出现的行才说明被分析的那段变了。原来两者走同一条判断，于是换排序之后旧分数还留在浮窗上——同一页里被分析的那批整段换掉，与换页是同一件事：一条都不在眼前了。现在：变多 → 保留分数 + 提示重算；被分析那段的行消失过半 → 撤掉分数。判据用"消失"而不是"新增"：换排序后新来的一批当然也是新的，但说明"换了"的是原先那批不见了；评论自然增长时旧行都在，它恒为 false。实测同一视频切排序（两份样本行重合度 17%）后十余秒内给出替换提示，人工追加长篇评论仍走"变多"分支 |
| 新增行的条数与比例都要看 | 绝对值管大页面，比例管小页面。两个数都是初值，要用真实使用校准 |
| 只比够长的行 | 相对时间与点赞数这类短行每次刷新都可能变，攒几条就够凑到阈值。代价：短回复不参与比对——它们本来也构不成"变化大"。实测：一批时间戳同时变不触发，另添若干长篇评论才触发 |
| 换页判断只比路径，不比完整地址 | 站点常在查询串里追加跟踪参数，比完整地址会误判成换页 |
| 比对跑在固定周期上，且只在页面可见时执行 | 站点一次就加载一批评论，更频繁没有意义；页面不可见时用户在别的标签页上 |
| 放弃"先看廉价信号、再比行集合"的两段式 | 廉价信号（容器子元素数）会漏掉"回复被展开"这类变化，而完整比对本来就要遍历一次 DOM，省不掉 |

### 扩展：进入网站时自动打开

| 做法 | 理由 |
| --- | --- |
| 按网站逐个申请 host 权限，也不申请 `tabs` | 安装时的"读取您在所有网站上的数据"会吓到人，也与"仅在需要时读页面"的立场相抵；逐站申请时，那句权限提示就只讲那一个站点。不申请 `tabs`：看不见地址就注入不了，权限本身就是功能的开关，不必再写一层"这个站点允不允许" |
| 请求授权落在扩展页面上，标题栏那个设置图标只负责开合 | 请求 host 权限必须在用户手势里发起，而内容脚本里没有 `chrome.permissions`，从后台的消息处理器里调也不算手势——Chrome 只认扩展页面上的那次点击。这不是设计选择，是平台规矩 |
| 授权界面嵌在浮窗里，不是另开窗口 | 嵌进来之后"再点一次收起"是自然的；独立窗口每点一次就多一个，用户得自己收拾 |
| 嵌入页自报高度，两端都认来源 | 跨源文档之间量不到对方高度，只能由嵌入页报回来。嵌入页发时指名目标来源，面板收时校验来源、窗口与消息形状——实测从页面本身伪造同样内容不会生效 |
| 嵌不进来就退到独立窗口 | 站点可以用 CSP 静默挡掉嵌进来的扩展页面。等不到高度就把设置区换成"加载失败"加一个按钮：宁可多一次跳转，也不要用户对着空白猜 |
| 失败文案只说哪一块没成，不猜原因 | 早先写成"这个网站不允许读空气在这里显示设置"，把原因归到站点上——用户更信站点，这句读起来像是我们被站点拒了；何况失败未必是站点的原因，我们本来就不知道 |
| 文案按"标准叫法 + 只说管什么"来写 | "收起"不写"最小化"（那是收进任务栏再取回），也不写"折叠"（界面里多指文本区块），它还和圆片上的"展开读空气"配成一对；设置区的标签要说出被打开的是什么、并限定范围（"当前网站"）。"开启后……""关掉即可"都在重复标签已经说清的事，不写 |
| 状态用开关，不用"开启/关闭"两个按钮 | 动词按钮要求用户把动词反过来读才知道当前状态；开关开态有颜色、关态是灰，状态自己说话。列表页保留"关闭"按钮——那里做的是"把这个站点移除"，不是翻一个布尔值 |
| 设置图标兼作状态：本站已开启时染成强调色，设置区展开时带一层底色 | 原来"已在本站自动打开"是一行字，去掉后状态就没地方说了；染色之后扫一眼就能看出这个站是不是开着。颜色取的是与图标同一个牌子色——同一种状态在两处用同一种颜色 |
| 图标用两根滑杆，不用齿轮 | 16px 下画齿轮会糊成一团；滑杆四条线段画得准，也更像"这里是一小块设置" |
| 授权页的底色一律不透明 | 次按钮与开关轨道原来是半透明白，衬在渐变上颜色会随位置变，对比度静态分析也算不准；换成同色相的不透明值，观感几乎一样，读数确定 |
| 触发点选"页面加载完成"，不理会站内换页 | 站内换页已由浮窗自己的"页面换过了"兜着，这里再插一脚就是两套逻辑做同一件事 |
| 授权页不自己关 | 开关都长在这一页上，一关就断了来回改的路径，也让没看清的人以为没办成 |
| 兜底窗口沿用浮窗那一套外观，落在屏幕中上位置 | 它是同一个产品在说话，不该长得像另一件东西（最初用的是浅色网页样式）；不指定位置时由系统决定，实测会跑到屏幕左下角，既不像一次提问，也离用户在看的地方远 |
| 授权名单记在 storage 里，而不是每次去读已授权的 host 权限 | 内容脚本要拿它决定设置图标染不染色，而它读不到 `chrome.permissions`；storage 的变更通知还顺带解决了"授权完成后图标要跟着变" |
| 关闭的两步收在 `shared/auto-open` 里，开启拆在页面里 | 关掉一个站点 = 名单去掉 + 权限还回，两步分开写迟早会漏一步；"开启"做不到合并——请求权限必须在用户手势里发起 |
| 设置页暂时不做"恢复默认设置" | 它服务的问题还不存在：窗口尺寸并不记忆，授权也能逐个关掉 |
| 隐私告知：第一次真的把文字发出去时说一次，设置里另留一个入口 | 两件事各管一半——提示管"第一次发生时知情"，入口管"事后可查证"；入口藏在设置图标后面，替不了提示。说在"发出请求"那一刻，不是"拿到结论"：文字离开浏览器发生在请求发出时，与模型答没答出来无关（第一次撞上"内容太少"时文字照样到了服务器，此时不说就得等到某次成功，告知晚于事实就不叫告知）。说过记在本地存储而不是会话存储（记会话会每开一次浏览器就说一遍），且是显示的那一刻就记下。不写"该声明只显示一次"——它对用户没有决策价值，一句话的版面该留给"发了什么、留不留" |
| 隐私声明关掉之后不再被重画回来 | 视图对象里带着"这一次要说说明"，而面板每次状态变化（点设置、收起再展开、设置区报高度）都会照着同一份视图重画一遍——关掉它，下一次重画它又跟着回来，用户读到的是"怎么每次分析都有"。**实测确认**：关掉后点一下"本站设置"，它立刻回来。现在面板自己记着"关过这一次"，重画时不再插它；说没说过仍由存储记（那是更长期的事，两者不是一回事） |
| 隐私文案的几条取舍 | 措辞集中在一处，免得一处改了另一处没改；不点名服务商（换个供应商就要改文案）；"外部"改"第三方"，与"自己的服务器"对照；原稿三句只讲我们怎样、没有回程，补一句"不想自动发送就在设置里关掉"；"服务器不保存这些文字"是读过代码确认的，所以可以照实写 |
| 对外防线：来源校验 + 按 IP 限流 + 每日上限 | 目的不是挡住有决心的攻击者，而是不让陌生人随手把地址当免费接口用——它后面挂着按量计费的模型。两道闸分工不同：来源挡"拿地址就试"，配额才是成本护栏（来源头可以伪造，配额不能）。位置放 `shared/web`（跨模块的 HTTP 边界关切），异常放 `shared/exception`（与业务无关），HTTP 翻译交给通用翻译器——于是扩展侧一行没改，被拒或被限流在它看来就是一次"分析服务暂时用不了"。计数放内存：单实例可接受、重启清零；多实例要换集中式，已写进技术设计。**冒烟实测**：无来源头 403、来源不在名单 403、名单内前两次已穿过防线（422 内容太短）、第三次 429。两道闸的值都是初值，按真实使用校准：每分钟那道只当粗糙刹车，设宽是因为共享出口 IP 的用户（校园网、公司网、移动网络）会共用它，设小了先误伤的是他们；真正的成本护栏是每日上限。429 也不单开文案，与"后端不可用"走同一条失败路径，有真实反馈再分 |
| 生产地址两处同源注入 + 商店上传包 | 地址硬编码会在发布时变成"忘了改"的错误，所以后台脚本与 manifest 的 host 权限必须同源：脚本由构建注入，manifest 由打包脚本改成同一来源。打包脚本拒绝非 https 与缺省值，免得把指向本机的包传上商店；sourcemap 留在开发产物里，上传包不带 |
| 隐私政策页由后端同域提供（`/privacy`） | 商店要求一个可访问的隐私政策地址，与接口同域最省事，也不必另找托管。页面对外可读，所以不在限流路径上——路径名单只管接口。静态资源只按文件名匹配，`/privacy` 自己找不到文件，所以在配置里加一条转发，而不是另写一个 Controller（shared 里放 Controller 会撞架构测试） |
| 图标：圆角方块 +"读" | 照的是 Chrome 给无图标扩展的默认方片观感——三个自画方案都被否掉，就认那一个；底色取界面上的主色，图标与界面同色才像一套。代价是汉字在工具栏最常走到的 16px 下糊成一个字形块。字的位置不靠目测：用画布量出墨迹范围再回推——也是从这一步开始，"改图标要重新渲染四个尺寸、位置靠实测"成了固定动作 |
| 图标换成一张平静的脸 | 上一条的代价躲不掉：汉字在 16px 下必然糊，而工具栏最常走到的正是那一档；换成形状更简单的记号，问题就从"识字"变成"识形"。试过的方向各有偏：波形与刻度柱读起来像数据工具，円相曲高和寡，青海波把品牌押在异文化上，火苗锁死在"冲突"这个未来只占一角的概念上。落在脸，是因为不识字也认得、比十个笔画简单，而且它不表态——产品是察觉，不是评判。底色取奶黄，界面里原来那个品牌蓝一并撤掉：主按钮改中性底，"已开启自动分析"这个状态的两处改用与图标同一个奶黄。这样界面上带颜色的只剩读数刻度；按钮若也跟着变暖，同一个面板里就会有两样东西都在说"热"，一个只是"重新分析"的按钮会被读成高温。源文件也随之改名，旧的那个已挪出仓库 |
| 按站点记一行用量 | 免费又没有账号，就没有别的反馈渠道：用户不会写邮件，也没地方留联系方式。能改变判断的信号只有三个——有人第二次用吗、分数准不准、哪些页面读不到。第三个只有服务端答得了，而服务端看到的来源是扩展 ID，不含站点，所以站点必须由扩展带上来。走请求头不走请求体：请求体是对外契约里"被分析的内容"，站点不参与分析，混进去迟早有人把它喂给模型，而指标是绝对值、不该随站点缩放。只记站点、状态与耗时，不记正文也不记页面地址；代价是隐私声明里"不发送网址"要改成"不发送完整网址"——宁可写清楚，也不能让声明与事实有出入。记录必须排在准入之前，否则被挡下的请求一行都不留 |
| 支持范围：只做 Chrome 与 Edge，只上 Chrome Web Store | 判据是内核门槛而不是感觉：正文提取依赖 `Element.checkVisibility()`（Chromium 105+），缓存与浮窗状态依赖 `chrome.storage.session` 与 `setAccessLevel`（102+），而 Chrome 与 Edge 本机都是 153，远超门槛。360 系本机没装、内核版本未知，且这类浏览器的内核长期滞后——为一个渠道去改动 Chrome 架构不划算，所以第一版不纳入，也不为它做兼容性工作。入口只留一个：Edge 用户从 Chrome Web Store 安装，代价是第一次要点一下"允许来自其他商店的扩展"（企业受管设备可能被策略封掉，属少数）。**顺带一个会反复踩的坑**：Chrome 与 Edge 自 137 起移除了 `--load-extension`，任何"命令行或自动化往正式版里塞扩展"的做法都不再有效（试过 `--enable-unsafe-extension-debugging`，无效）；手测只能在扩展页点"加载已解压的扩展程序"，要自动化就得退到 Chromium 或 Chrome for Testing。兼容性矩阵就是这么跑的：**实测 Chrome for Testing 153 上，装扩展、Service Worker、storage 三项、调后端、设置页渲染、真实页面上的影子根可达全部通过**。要复跑就用同一套路：Playwright 起 Chromium（或 Chrome for Testing）、加载 `dist`、在它的 service worker 里探 API |

## 二、过程中总结出来的判断依据

这部分不描述项目现在长什么样，只回答"这类事往哪边定"。

**强制只用在不可逆的地方。**
用户自己能判断、能撤销的事，不由产品替他锁死：窗口能拖到多小、要不要自动打开、要不要重算，都是他的事。产品只守住真正越不过去的那条线——窗口小到控件自己装不下就不能再小，因为那时他连"收起"都点不到，丢的不是读数，是回程。

**给了控制权就要给回程。**
只给开关不给撤销，不是授权，是甩锅。每个"打开"旁边都该有"关掉"。

**用户没要求的动作不做。**
不替他滚页面、不替他重算、不替他发请求：这些动作要么动了他的页面，要么花了他的钱，而收益只是"也许能多看一眼"。要动，就由他点一下换来。

**只描述事实，也不让用户替我们猜。**
我们说不准的事就别猜：没读到内容时不猜页面类型，设置区加载失败时不猜是站点挡的，按钮不预设"滚过去就有"。反过来，界面上的读数要自带名字——一个孤立的数字不能被当成"这页的评分"，得写清它量的是什么、哪一端才算糟。

**命名一条度量时，别拿它最高一档的词当全局名字。**
轴名要覆盖整段范围。用最高档的词命名全局，会把中段也念成那个词——与自己写下的分档打架。往未来看也一样：多条轴并列时，轴名之间要能彼此划清，语义重叠的词更难分家。所以名字分三层各管一处：契约名要稳定（改它得重跑校准）、定义名要说准、界面名要跟数字读得通。

**数值从实测来，不从感觉来。**
等待门槛、容器等待、窗口形状、条数口径，几处初值都被实测推翻过（门槛让短页面白等；窗口只取开头让"取到哪一批"决定结论）。定数值之前先问"拿什么量它"。

**两道闸要分工，别指望一道管全部。**
挡"随手拿地址就试"的是一道，兜住成本的另一道，两者的对手不同：只有前者，被绕过就是无限账单；只有后者，正常用户会和攻击者抢同一份额度。说清各自防的是什么，才知道该把哪个调紧。

**能让平台约束替我们做判断的，就不自己再写一层。**
不申请 `tabs` 权限——看不见地址就注入不了，于是"这个站点允不允许"不必再判断一次。

## 三、记下来的数据

量这些时的条件：模型 `deepseek-chat`，口径里 `temperature = 0`；口径与分档自 `641485f`（09-14）起未再改动，窗口与等待的数据在 `a0edf76`（09-15）到 `6ee780f`（09-19）之间陆续取得，界面相关的在 `d5e6bd8`（09-19）。

- **评测基线与校准**：五段样本各跑两次核验——平和 5/5、争论 45/58、对立 78/78、骂战 88/88，附和那段两次都回 422「内容不足以分析」。另用 5 段真实 B 站讨论各跑 3 次校准：5 / 18 / 38 / 42 / 72，档位依次平和、平和、还算理性、争论明显、对立明显；四段三次完全一致，只有最平和那段出现过 12/18/22。两处要留意："对立"那段贴着自己档位的上沿，"争论"那段两次差 13 分——改口径时它们最可能先变红。模型单次判断（5–10k 字输入）0.6–1.3 秒。
- **等待与响应**：点图标到浮窗出现几乎实时；内容已渲染的页面不到 1 秒出结果；需要搬运评论区的页面约 2.4 秒（等稳定 + 模型判断）；改掉字数门槛之前同一页面要等 8.5 秒。分批到达的页面（每 300ms 一条）：最后一条之后约 1.5 秒开算，样本含最后一条。用户的等待几乎全部来自模型判断。
- **窗口与"有新变化"的实测**：12899 字 / 386 行的知乎问题页，送出的窗口 9845 字 / 296 行，每行完整、首尾都在。稳定性（把讨论缩短后再取一次）：缩到 95% / 80% / 50% 时，旧窗口仍有 90.6% / 81.3% / 74.1% 的行留在新窗口里（"整段被替换"的阈值是消失过半）。触发门槛：短 0.5% → 新增 4 行不触发，短 2% → 7 行不触发，短 5% → 37 行触发——也就是要长到 3–4%（几百字）才会提示一次。
- **换排序的实测（两段视频）**：彩礼那条（5556 字）最热与最新两份样本行重合度 17%，分数 38 与 42——两批氛围相近，**不能据此说"分数对抽到哪一批不敏感"**；华为小米那条（最热 7957 字、最新 14286 字）最热 42、最新 62，差 20 分跨一档——最新排序的前排是近期短促的对骂，最热的前排是高赞的长篇数据对比。**"取到哪一批"确实能改变结论。**
- **截断代表的四次尝试**：前三次都问不出什么（同一视频的前中后窗口、换排序的两批、跨八个月的两个 7000 字窗口）——样本在"氛围"这个维度上是均匀的。第四次按"塌房明星"找（23705 字，评论跨 2022 年塌房当时到 2026 年）：三千字窗口给 42 与 62，说明**样本内部确实不均匀**；一万字窗口前后段都是 62。与直觉相反：最激烈的是塌房当时的 2022 年，四年后的围观反而平静。

## 五、想法区

**这一部分不受文档规范约束：想到什么写什么，包括可能不靠谱的。写在这里不代表已经决定，回头翻的时候按当时的情况重新判断。**

### 想过，还没定

- **桌面吉祥物**：用颜色表达情绪这件事，更适合交给一个有形象的角色（QQ 宠物、瑞星小狮子那种路子：心情好偏蓝绿，生气就红温），而不是撒在控件上的色块。MVP 不做，先记着。
- **两种配色（深色 / 米白）在设置里可选**：定在上线后做。做之前先备好三件事：颜色现在散在面板与设置页两处的内联样式里，得先收成一组变量，否则两套配色会散在四个文件里；三条踩过的约束要各自重推（半透明必须配描边与模糊、压在毛玻璃上的浅色文字要留够对比度、授权页底色不透明以便静态算对比度）——浅色面板压在浅色页面上靠的是描边与阴影，不是把色值反过来；偏好存在存储里，读它是异步的，得决定"等读完再画"还是"先藏住宿主"，否则会闪一下。
- **六芒星：六个指标，每个角可由用户编辑**：定在上线后评估。现在这套的支点是"一个绝对值、跨页面可比、口径与抖动都量过"，六轴等于六条口径各校准一遍（今天这条是 5 段 × 3 次的量级），而且轴之间天然相关——"阴阳怪气"与"敌意"高度相关，形状会骗人。动手前先回答：用户编辑的是名称、权重，还是加不加这一轴？两件事现在守住就够了：别让"骂战"成为产品的自我定义（模块名是中性的，文案也不用它当全局名字）；契约形状本身是加法可扩展的（多轴只多一个数组字段），不预抽。

### 想过，目前不做

- **文本去重**：会削掉"一大片同感"这类本该计入的样本。
- **MutationObserver**：新建的 shadow root 不会触发宿主上的 observer，"发现新 shadow root"本身还得轮询——除非去改页面主世界的 `attachShadow`。
- **固定条数上限**：停止条件已经是"够样本且稳定"，条数上限是同一意图的另一种表达，不必并存。
- **静默加载更多页**：容量这一环已经接住（窗口摊在整段上，读得越多越有代表性），不做是因为**不愿动用户的页面**——目前允许的位移只有用户自己点按钮换来的那一次。
- **自动重算**：体验最好，但要额外授权（点过一次分析不等于授权持续把页面内容发往服务器）、要控制成本。仍只做提示——重算要花钱，而"要不要多看一眼"用户一眼能判断。
