# 读空气 开发记录

这是一份开发过程记录，不是设计说明。

它与文档规范有意冲突：按 [AGENTS.md](../AGENTS.md) §8，文档只描述最终状态，不保留历史方案、被取代的做法与修改过程；而本文恰恰要留下演进——比如"停止条件为什么从 2000 字改成了另一个值"，这类信息别处没有地方放，忘掉之后容易被重新提议。

因此本文的约定是：

- **当前的设计与结构以 [03-技术设计.md](03-技术设计.md) 和代码为准**，本文可能与其不一致；
- 做法变化时，在对应条目下补一行说明变化与原因，不改写原记录；
- 发现旧记录有明显错误时，就地加批注说明，不抹掉原样。

前半是已经开发过的做法与理由，后半是想法区——想到什么写什么，不代表已经决定。

## 一、已开发

### 后端：空气分析接口

| 做法 | 理由 |
| --- | --- |
| 公开契约只收页面文本，不收标题与地址 | 指标描述的是讨论自身的对抗性，是绝对值，不该随站点或话题缩放。实测带与不带这两项，评分没有实质差别 |
| 模型返回的分值越界时判为非法结果，不夹取到范围内 | 夹取会把一次失败的调用伪装成有效结论，宁可让这次分析直接失败 |
| 失败分成"内容不足"与"服务不可用"两类 | 前者要用户换页面，后者要用户稍后重试，提示、状态码、日志级别都不同 |
| "读不出来"是一等结果，不折算成分数 | 只有零散附和或导航文字的页面，曾经会拿到 0 分、置信度接近 1.0——用户读到的是"这里很平和"，实际含义是"读不出来" |
| 后端只给等级代码，中文措辞交给扩展 | 措辞会反复调整，不应进入契约 |
| 评分口径集中在一个提示词类里 | 换模型或调口径只动一处 |
| 内容下限与截断长度是暂定值 | 需要真实页面校准，预期会改 |
| 评测基线用三段样本跑真实模型，默认不进 CI | CI 没有模型密钥；只在改提示词或换模型时手动跑 |

### 扩展：骨架

| 做法 | 理由 |
| --- | --- |
| 点击工具栏时才注入内容脚本，不声明常驻脚本 | 常驻脚本在每个页面都会运行，与"仅在用户主动请求时读取页面"相抵；权限因此只需 `activeTab` 与 `scripting`，安装时不会要求读取所有网站数据。（后来加了按网站授权，见「扩展：进入网站时自动打开」：仍是用户看过哪一页才读哪一页，只是把权限换成了逐站申请） |
| 请求交给后台 Service Worker 发出 | 内容脚本受页面 CORS 限制，后台不受 |
| 浮窗渲染收在一个文件里，其余文件与 UI 无关 | 将来浮窗复杂度上来要换 UI 技术时，只替换这一层 |
| 后台、内容脚本与授权页各构建一趟 | MV3 的内容脚本不是模块，产物里不能出现 `import`，而 Vite 的多入口模式在 IIFE 格式下不可用，所以脚本各自打一份；授权页是普通扩展页面，按模块打包即可 |
| 重复注入时复用宿主元素、换上新监听器 | 工具栏每点一次就会注入一次。"宿主元素在不在"不能代表"当前扩展上下文里有人监听"：扩展重新加载后，页面里还留着上一版脚本的宿主元素，旧监听器已经随旧上下文失效。曾据此提前退出，结果浮窗彻底打不开（后台报 `Could not establish connection`），只能靠刷新页面恢复 |

### 扩展：页面正文提取

| 做法 | 理由 |
| --- | --- |
| 逐节点遍历并下钻 shadow root，不读 `body.innerText` | 视频站与论坛的评论正文常渲染在 shadow root 内，读 body 只能拿到页面框架 |
| "未就绪"与"读到空内容"分开判断 | 页面刚打开时讨论容器可能还没挂载，此时若回退整页，会把导航与推荐位当成讨论正文 |
| 站点差异集中在"站点期望表 + 通用回退"一处 | 只有一个实现时，接口形状取决于第二个站点的真实样子，现在抽接口等于先付一次、将来再付一次 |
| 提取起点收进评论列表内部，跳过列表头部的计数与排序控件 | 那些是页面控件，不是讨论内容 |
| 只取文本，不解析单条评论、用户名、点赞、楼层 | 逐条解析会把最容易变的 DOM 结构写进采集核心，而分析并不需要这些字段 |
| 不调用站点接口，不做签名与逆向 | 签名算法会变、要处理风控，而且它是站点专有的，换个站点等于重做 |

### 扩展：触发加载与等待

| 做法 | 理由 |
| --- | --- |
| 触发懒加载用"无感搬运"：给讨论容器加 `position: relative; top` 与 `opacity: 0`，只在视觉上把它挪进视口 | 评论要进入视口才加载，而滚动必然移动用户页面。相对定位不参与布局，容器原位与页面滚动位置都不变，用户察觉不到 |
| 用相对定位，不用 `transform` | 自定义元素默认是 inline，`transform` 对 inline 无效，得先改 `display`，那会引起重排 |
| 只在容器不在视口内时才搬 | 容器已经在视口里，说明页面自己在加载，此时透明化等于把用户正在看的内容藏起来 |
| 样式在结束时必须还原 | 否则容器会一直停在透明、不可交互的状态 |
| 面板显示中间态"正在读评论区…" | 搬运期间页面没有任何变化，缺少中间态会让用户以为点击没反应 |
| 停止条件是"样本 ≥ 2000 字且连续两次快照一致" | 一读到内容就停，样本量会随加载进度浮动，同一页面的分数失去可比性 |
| 采集有 8 秒总上限，超时就用已有内容 | 任何路径都不允许无限等待 |
| 无感加载失败时退回真实滚动，且先给按钮由用户触发 | 位移必须由用户换来 |

### 扩展：分析链路

| 做法 | 理由 |
| --- | --- |
| 响应体在扩展侧过一道结构校验 | 后端是外部系统，返回结构不受编译期类型约束；缺字段或出现陌生的等级代码时，面板会渲染出 undefined 或空白 |
| `host_permissions` 先只声明本机后端地址 | 部署地址确定之前不扩大权限范围 |
| 等级措辞与失败文案都放在扩展侧 | 后端只给代码与状态；措辞会反复打磨，不该进契约 |
| "服务不可用"与"网络不通"对用户合并成同一句 | 两者对用户是同一件事——过会儿再试——让他去分辨一个自己无能为力的差异没有意义。代价：与后台断连时同样无法从面板分辨，调试时曾因此多绕一步（日志里仍分得清） |
| 置信度低时只加一句"这里的内容不太好判断" | 用户不需要知道 0.85 这样的数字，只需要知道这次判断不太牢靠 |
| 改动 manifest 或后台脚本后必须重新加载扩展 | 这两样只在扩展加载时更新，而注入的内容脚本是按文件取的；调试时曾因此看到"面板已是新文案、后台却没有监听者"的假象 |

### 扩展：浮窗交互

| 做法 | 理由 |
| --- | --- |
| 位置与折叠状态放在渲染层的模块状态里，每次渲染再套回元素 | 面板每次状态变化都会整体重建，位置不能跟着丢 |
| 只有标题栏可拖，圆片整块可拖 | 正文里要能选中文字、点按钮；圆片没有别的内容 |
| 指针移动超过 4 像素才算拖动，否则当成一次点击 | 同一套指针处理要同时支持"拖圆片"和"点圆片展开" |
| 拖动时与视口变化后都把位置夹在可见范围内 | 否则浮窗会被拖出屏幕，只剩"再点一次图标"这种很隐蔽的恢复方式 |
| 浮窗自带 `position: fixed` 与最高 `z-index` | 宿主元素排在文档流末尾：少了定位，圆片会落到页面底部；少了 `z-index`，会被站点浮层盖住，连拖都拖不动——这两处都是实测踩到的 |
| 面板与圆片共用同一套表面：深色毛玻璃，带描边与背景模糊 | 收起前后应当是同一个东西；半透明必须配描边与模糊，否则它在浅色页面上会糊成一片 |
| 圆片保持中性，不按等级上色 | 客户端上的彩色块容易被读成游戏化的装饰，与工具的气质不合；"用颜色表达情绪"更适合交给一个有形象的角色，见想法区 |
| 四条边与四个角都能拖 | 拉窗口这件事，八个方向都得有；用户朝某个方向拖时不该什么都不发生。曾经只有左、右、下与两个下角，上边是后来补的 |
| 拖哪条边，对面的那条边就不动：拖左边缘时右边缘固定，拖上边缘时底边固定 | 拉窗口就是这么回事；若反过来（整个面板跟着动），手感会变成"在搬东西"而不是"在改尺寸" |
| 内容区独立滚动，标题栏固定 | 面板能被拖矮之后，内容必须能在里面滚，否则会把标题栏顶出去。实测拖到下限 90px 时内容开始滚、标题栏位置不变 |
| 高度默认由内容撑，用户拖过之后才固定 | 内容长短不该由我们猜：默认贴合内容，用户拖过之后按他的意思来 |
| 宽高上限都跟着屏幕走，不设固定数值 | 曾经把宽度上限写成 460，实测中很容易撞到；上限应当表现为"到头了"，而不是"撞上一个数字"。宽度的上限是"两侧各留出贴边留白后还剩多少"，高度的上限是"顶边到屏幕底部还剩多少"，拖上边时则是"底边到屏幕顶部还剩多少" |
| 宽度下限 80px、高度下限 56px | 下限定在"标题栏的两个按钮还够得着"，不定在"字好不好读"：用户要把窗口压细，多半是因为它挡住了页面上的东西，这时他在意的是窗口有多小，不是窗口里的内容好不好看。曾经按可读性定成 240，属于替用户做了不该做的判断 |
| 窗口很窄时先牺牲标题，两个按钮始终留得住 | 下限要能压到 80px，标题栏就得会退化。标题截断只是丢了个名字，按钮被挤出去就真的关不掉了。实测 80px 时标题只剩 8px、按钮完整可点，收起与关闭都正常 |
| 文字重排不做任何处理 | 宽度一变，浏览器就按新宽度折行、高度自己跟着变。实测 240 宽时面板高 248px，460 宽时 184px |
| 变宽越过右边缘时把面板整体左移，而不是限制宽度 | 面板默认就停在右上角，限制宽度会让它连默认宽度都回不去 |
| 缩放热区平时透明，指针移到面板上才显形 | 它们不该破坏浮窗的外观；这也让"窗口不该不能缩放"这个直觉有处安放 |

### 扩展：结果过期检测

| 做法 | 理由 |
| --- | --- |
| 比对范围就是被分析的那一段：扩展自己截取前 10000 字发出 | 后端那道截断只是兜底。若比对整页，用户只是往下翻、让窗口之外加载出更多评论，也会被提示"内容变了"，而分数本来就没覆盖那些内容 |
| 基线取刚送去分析的那段文本，而不是分析返回后重读页面 | 分析与返回之间页面可能又加载了内容，那些内容并没有被这次分析覆盖，不该被当成已分析 |
| 比对按行集合做，只看新增行 | 评论逐条出现，新出现的行才说明分析覆盖的那段变了。变多与换排序（整段被替换）都走这条判断 |
| 阈值：新增行 ≥ 10 条，或新增行占当前行的 20% | 绝对值管大页面，比例管小页面。两个数都是初值，要用真实使用校准 |
| 换页判断只比 `pathname` | 站点常在 query 里追加跟踪参数（B 站的 `vd_source`、`spm_id_from`），比较完整地址会把它们误判成换页。实测 B 站切换评论排序也不改地址，所以排序变化会落到内容判断上，不会被误报成换页 |
| 同页内容变化时保留旧分数，只加一句提示与重算按钮 | 那个分数没有错，只是样本变了；而整页换掉时不给旧分数——它跟当前讨论毫无关系 |
| 比对周期 10 秒，且只在页面可见时执行 | B 站一次加载 20 条评论，比这更频繁没有意义；页面不可见时用户在别的标签页上，更没必要读这个页面 |
| 放弃"先看廉价信号、再比行集合"的两段式 | 廉价信号（容器子元素数）会漏掉"回复被展开"这类变化，而完整比对本来就要遍历一次 DOM，省不掉；10 秒一次的开销可以忽略 |

### 扩展：进入网站时自动打开

| 做法 | 理由 |
| --- | --- |
| 按网站逐个申请 host 权限，不在安装时就要全站权限 | 安装时的"读取您在所有网站上的数据"会吓到人，也与"仅在需要时读页面"的立场相抵；逐站申请时，那句权限提示就只讲那一个站点 |
| 请求授权落在一个独立的扩展页面上，浮窗底部那一行只负责把它打开 | 请求 host 权限必须在用户手势里进行，而内容脚本没有 `chrome.permissions` 这个 API，从后台的消息处理器里调也不算手势——Chrome 只认扩展自己的页面上那一次点击。这不是设计选择，是平台规矩 |
| 授权成功后自动关掉那一页 | 它只是从浮窗拐出来的一步，用户要回去的是原来那个页面 |
| 授权名单记在 storage 里，而不是每次去读已授权的 host 权限 | 内容脚本要拿它决定浮窗底部那一行的措辞，而它读不到 `chrome.permissions`；storage 的变更通知还顺带解决了"授权完成后浮窗上的字要跟着变" |
| 自动打开的开关放在浮窗底部一行，不进标题栏 | 标题栏是"收起、关闭"两个动作，再塞一个入口就挤了；底部一行既在视野里，也不打断读数 |
| 触发点选"页面加载完成"，不理会站内换页 | 站内换页（地址变了但没有重新加载）已经由浮窗自己的"页面换过了"兜着，这里再插一脚就是两套逻辑做同一件事 |
| 不申请 `tabs` 权限，未授权站点的地址读不到 | 权限最小化，而且它正好就是功能的开关：看不见地址就注入不了，不必再写一层"这个站点允不允许"的判断 |
| 已授权的站点每次加载都会重新分析一次 | 这是"进站即读"的代价，结果还没有缓存可复用（缓存是后面的事）。关掉浮窗不会改变这一点，要停就去设置里关掉这个站点 |
| 底部那一行的文字透明度不低于 0.8 | 它压在毛玻璃上，而毛玻璃的底色跟着页面走：0.6 在亮页面上会把 13px 字的对比度压到 4 左右，正好卡在 4.5 这条线下面 |

## 二、想法区

**这一部分不受文档规范约束：想到什么写什么，包括可能不靠谱的。写在这里不代表已经决定，回头翻的时候按当时的情况重新判断。**

### 想过，还没定

- **桌面吉祥物**：用颜色表达情绪这件事，更适合交给一个有形象的角色（QQ 宠物、瑞星小狮子那种路子：心情好偏蓝绿，生气就红温），而不是撒在控件上的色块。MVP 不做，先记着。
- **分数该测哪一段（已搁置）**：现在是固定取开头的约一万字——好处是跨页面可比（"哪个视频更吵"问得通），代价是窗口满了之后再往下翻不再提示、"讨论后段才升温"也永远不反映。另一条路是窗口跟随阅读位置：在页面顶部点图标时它会退化成开头那段（比较性仍在），只有人真的在读评论时才定位到本地；代价是同一页面可能出现两个分数，得靠面板标注读取范围化解。这条先不动，等真实使用后再判。
- **自动重算**：体验最好，但要额外授权（点过一次分析不等于授权持续把页面内容发往服务器）、要控制成本，还得让分数变化看得见。先只做提示。
- **2000 字 / 500ms / 8 秒这组数值都是初值**：需要用真实页面校准。
- **面板显示"读了 N 条评论"而不是"N 字"**：更好懂，数列表容器的子元素就够，不必解析每条。
- **静默加载更多页**：把"下一页"也搬进视口就行，但样本会从三千字涨到几万字，直接撞上后端的 10000 字截断。要不要做取决于截断怎么处理。
- **后端 10000 字截断是否改成均匀取样**：现在等于只看靠前的评论，同一页 3.6k 与 37k 的分数差异还没测过。
- **第二个站点（知乎、微博）怎么适配**：已用一个论坛页实测，现有提取器能取到内容，但混入导航与广告。补站点表还是改噪音过滤，未定。
- **扩展内的隐私告知**：03 §十八 要求明确告知用户内容会发往服务器，目前一处都没有，放哪、怎么写也还没想。

### 记下来的数据

- **响应速度基线**：点击图标到浮窗出现几乎实时；"正在读评论区"基本感知不到（该页面的评论已经加载好，这步被直接跳过）；"正在判断空气"约两三秒——用户的等待几乎全部来自模型判断。以后调优拿它对比。

### 想过，目前不做

- **逐条评论解析、按条数计数（20/50 那种）、文本去重**：去重会削掉"一大片同感"这类本该计入的样本。
- **MutationObserver**：新建的 shadow root 不会触发宿主上的 observer，"发现新 shadow root"本身还得轮询——除非去改页面主世界的 `attachShadow`。
- **采集器接口 + 每站一个实现类**：等第二个站点真的落地，看两者的差异长什么样再抽。
- **`scrollIntoView` 触发 + 采集后恢复滚动位置**：被无感搬运取代，连"恢复位置"这个需求一起消失。
- **进入页面就自动采集或预热**：与"仅在用户主动请求时才把内容发往服务器"冲突，而且自动触发必然移动页面。
- **固定条数上限**：停止条件已经是"够样本且稳定"，条数上限是同一意图的另一种表达，不必并存。
- **通用爬虫框架、事件总线、插件系统**。

### 还没验证

- **真实点击工具栏**：受扩展权限模型限制，需要用户手势，我模拟不了。
- **兜底滚动路径**：缺一个能让无感加载失败的真实页面。如果各站点都支持无感，这条路径可能变成死代码。
- **加载很慢 / 评论区始终不出现 / 评论数量不足**这三种情形。
