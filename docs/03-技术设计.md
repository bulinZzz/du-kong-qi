# 读空气 技术设计

## 一、技术目标

读空气的第一阶段是一个浏览器扩展与后端服务组成的 AI 产品。

技术实现需要解决的核心问题并不复杂：

> **从用户当前浏览的网页中获取具有分析价值的内容，将其交给 AI 判断“空气”，再以足够快、足够稳定、足够直观的方式返回给用户。**

MVP 优先保证：

* 链路简单；
* 结果稳定；
* 响应速度可以接受；
* 用户隐私边界清晰；
* 后续能够继续扩展。

不为了展示技术能力而引入不必要的复杂系统。

---

# 二、总体技术形态

产品由两个主要部分组成：

```text
Browser Extension
        │
        │ HTTPS
        ↓
Backend Service
        │
        ↓
LLM Provider
```

### Browser Extension

负责：

* 获取当前网页内容；
* 接收用户操作；
* 展示分析状态；
* 展示分析结果。

### Backend Service

负责：

* 接收分析请求；
* 处理和规范化网页内容；
* 组织 AI 分析；
* 校验分析结果；
* 向 Extension 返回统一结果。

### LLM Provider

负责：

* 根据页面内容进行空气分析。

LLM 属于外部能力，不属于产品自身的业务核心。

---

# 三、技术栈

## Browser Extension

MVP 计划使用：

* TypeScript
* Vite
* Chrome Extension Manifest V3

MVP 不引入前端框架：浮窗只有未分析、分析中、结果与失败几种状态，直接操作 DOM 足够。
等浮窗复杂度（多指标、自定义提问、空气历史）上来之后，再评估是否引入 React。

第一阶段优先支持 Chromium 系浏览器。

## Backend

MVP 计划使用：

* Java
* Spring Boot

# 五、页面内容获取

这是 Extension 的第一个关键技术问题。

产品需要从当前网页中提取能够代表页面主要内容的文本。

第一阶段的原则是：

> **优先获取当前页面中用户实际能够看到的主要文字内容。**

不追求一次解决所有网站。

MVP 可以先针对：

* 论坛；
* 社区；
* 评论区；
* 新闻评论；
* 其他文字讨论密集型页面

进行验证。

---

## 内容处理流程

```text
当前网页
   ↓
获取页面文本
   ↓
过滤明显无关内容
   ↓
清理空白和重复内容
   ↓
控制内容长度
   ↓
发送 Backend
```

需要重点处理的问题：

* 动态加载；
* 无限滚动；
* 导航和菜单干扰；
* 重复文本；
* 页面内容过长；
* 页面几乎没有文字。

第一阶段不使用 OCR。

---

## 站点适配

站点差异集中在一张"站点期望表"里：每个已适配的站点给出承载讨论的容器，其余站点走通用回退（按语义容器找，都找不到才用整页）。

判据是**容器在不在**，不是**这一页该不该有讨论区**。同一个站点的页面类型数不清，为每种页面维护一条判断既补不全、又会随改版失效；而"容器在不在"只有两种结果，正好对应我们能说的两件事：读到了，没读到。

| 站点 | 讨论容器 | 一条内容叫什么 | 那个站点自己的样子 |
| --- | --- | --- | --- |
| B 站 | `bili-comments` 里层的内容区 | 评论 | 要进入视口才渲染 |
| 知乎 | `#QuestionAnswers-answers`（一条条数 `.AnswerItem`） | 回答 | 加载时就已渲染；评论要点开才加载，页面里没有 |
| 微博移动站 | `.comment-content` | 评论 | 加载时已渲染出前二十条，往下滚继续追加 |

浮窗因此说"读了其中约 N 条评论"，知乎上说"读了其中约 N 条回答"——**不替站点编一个通用的词**。

条数数的是"窗口覆盖到几条"：知乎的问题页有几百个回答，一万字摊下来只是其中几条，报出去的必须是结论真正覆盖到的那几条。没适配的站点不报条数——认不出"一条内容长什么样"的地方，一个数字只会让它显得比实际更可靠。

知乎的首页、热榜、专栏页与单回答页都没有这个容器，一律按"没读到"处理：它们给的是一份信息流或一篇文章，不是讨论。

微博桌面站（`weibo.com`）则是另一种情况：评论在，但装在虚拟列表里，DOM 里只留当前视口附近的几条，滚动时整批换掉——讨论本身没变，眼前这一段却换了人。所以暂时不接，只接移动站。

---

## 界面文字

评论列表里混着页面自己的控件文字：时间、"共 70 条回复，点击查看"、孤立标点、"回复"这类动作标签。两份真实样本实测各占 **31% 与 32%** 的字数——一万字的窗口里近三分之一被它们吃掉，相对时间还会随时间变，给"讨论有没有变化"的比对添噪声。

处理方式是**按行的形态丢，不按站点结构丢**：结构每个站点都不一样，而"一条时间戳长什么样"是通用的。丢完之后若一行不剩，就按"没读到"处理。

这份占比因站点而异，规则不跟着站点调：知乎的讨论是长文答案，页面自己的文字（作者名、徽章、"N 人赞同了该回答"）实测只占容器字数的 1.1%，不值得为它加规则。

用户名不在此列：它和"同感"这类短回复长得一样，通用规则分不开，要靠站点自己的结构去认——站点适配里还没做这件事。

---

## 没读到内容

提取只有两种结果：读到了，没读到。"没读到"不细分原因——想分出"这一页该不该有讨论区"，就得为每种页面维护一条判断，而页面类型是列不完的（同一个视频站就有首页、搜索、动态、直播间、课堂、会员购……）：这张表补不全，还会随站点改版失效。

所以：

* 不向用户断言原因，不说"还没加载"，也不说"这一页没有讨论区"，只说没读到；
* 要不要再试一次交给用户判断——他就在那一页上，比我们清楚，所以按钮的措辞也不预设"滚过去就有"；
* 授权站点上自动打开时，只有读到内容才出现：没读到就不显示浮窗，也不闪加载态。

---

# 六、分析请求

Extension 向 Backend 提交当前页面的分析请求。

请求携带页面主要文本。

Backend 不依赖浏览器本身提供的“网页语义”，而是将收到的内容重新组织为标准化分析输入。

这样可以让不同浏览器或未来其他客户端都使用同一套分析能力。

---

# 七、AI 分析

MVP 的 AI 能力非常集中：

> **判断页面当前的骂战激烈程度。**

第一阶段不构建复杂的多模型系统。

基本流程：

```text
页面内容
   ↓
输入规范化
   ↓
分析上下文构建
   ↓
LLM
   ↓
结构化结果
   ↓
结果校验
```

---

# 八、Flame Intensity

核心指标：

> `Flame Intensity`

范围：

> **0 ～ 100**

它表示页面整体的冲突、敌意和情绪升级程度。

需要特别避免：

> **把“观点不同”直接当成“骂战激烈”。**

评分应该重点关注：

* 人身攻击；
* 敌意；
* 讽刺；
* 情绪化表达；
* 阵营对立；
* 语言升级；
* 交流是否已经明显偏离理性讨论。

---

# 九、评分 Rubric

为了减少 LLM 的主观漂移，需要为评分提供明确的判断标准。

初始范围可以划分为：

```text
0–20
基本平和

21–40
存在不同观点，但整体仍然理性

41–60
争论明显，开始出现较强情绪

61–80
对立明显，攻击、讽刺或情绪升级较多

81–100
高度激烈，形成明显骂战
```

这些范围不是最终标准。

MVP 实际运行后，需要根据真实页面进一步调整。

---

# 十、结构化输出

LLM 不应直接返回一段不可控的自然语言作为最终结果。

希望得到结构化结果，例如：

```json
{
  "flameIntensity": 87,
  "summary": "观点对立明显，情绪已经明显升级。",
  "evidence": [
    "存在明显的人身攻击",
    "参与者之间出现持续性的敌对表达"
  ],
  "confidence": 0.91
}
```

Backend 对结果进行基本验证：

* 字段是否完整；
* 类型是否正确；
* 分值是否在 `0～100`；
* 内容是否满足基本约束。

如果模型返回无法解析的结果，Backend 应进行错误处理，而不是把原始模型输出直接传给用户。

---

# 十一、LLM 与 Backend 的边界

LLM 是外部依赖。

Backend 不应让产品核心逻辑直接绑定某个具体模型供应商。

推荐的关系：

```text
Application
      ↓
LLM 能力抽象
      ↓
具体 Provider
```

这样未来可以更换模型供应商，而不需要修改核心业务逻辑。

第一阶段不需要支持多个 Provider。

---

# 十二、Backend 架构原则

第一阶段业务非常简单，因此不人为制造大量领域对象。

核心业务大致围绕：

```text
Atmosphere Analysis
```

展开。

基本职责边界：

```text
Web
 ↓
Application
 ↓
Domain

Infrastructure
 └── LLM / 外部系统
```

Application 负责：

> **编排一次空气分析。**

Domain 负责：

> **表达和约束分析结果。**

Infrastructure 负责：

> **与 LLM 等外部技术细节交互。**

---

# 十三、Extension 与 Backend 的职责边界

## Extension 不负责

* LLM 调用；
* LLM API Key；
* Prompt；
* 核心评分规则；
* AI 输出判断。

## Backend 不负责

* 操作网页 DOM；
* 控制浮动窗口；
* 处理浏览器 UI；
* 决定用户界面表现。

两边通过明确的 API 通信。

---

# 十四、缓存

页面内容可能在短时间内被重复分析，因此 MVP 可以考虑缓存。

基本思路：

```text
页面内容
   ↓
生成内容 Hash
   ↓
查询缓存
   ↓
命中 → 直接返回
未命中 → 调用 LLM
```

缓存主要用于：

* 降低 LLM 成本；
* 缩短响应时间；
* 减少重复分析。

第一阶段不需要复杂的分布式缓存方案。

---

# 十五、输入长度

网页内容可能远大于模型适合处理的长度。

因此需要建立统一的输入处理策略。

基本流程：

```text
页面文本
   ↓
清洗
   ↓
去除明显无关内容
   ↓
控制长度
   ↓
提交分析
```

长度控制是一万字的窗口，但**不是从开头切一刀**：整段讨论摊成五处并列的窗口——第一处贴开头、最后一处贴结尾、中间等距铺开，各自取满预算（各两千字）。

这么做是因为"只取开头"会把结论绑在排在最前面的那批上：讨论发生反转时，新声音在开头还很稀疏，取开头报出来的是旧气氛。窗口按行取，边界落在行与行之间，不在句子中间切开。

窗口定在扩展一侧：送去分析的是它，判断"讨论有没有变化"比对的也是它。后端还会按同样的长度兜底截断一次，防超长输入。

第一阶段不追求对无限长度页面进行完整分析。

---

# 十六、响应速度

读空气属于轻量工具。

如果用户：

> 点击 → 等待很久 → 才看到结果

产品体验会明显下降。

因此需要重点关注：

* 文本提取速度；
* Backend 请求耗时；
* LLM 响应时间；
* 缓存命中率。

实测（B 站真实页面）：页面上的讨论已经渲染好时，点图标到出结果不到 1 秒；需要把评论区搬进视口并等它渲染时约 2.4 秒，其中等渲染稳定 1.5 秒、模型判断约 1 秒。等待由这两段分摊，其余都可忽略。

MVP 阶段先采用同步请求。

是否需要流式响应，之后根据实际体验决定。

---

# 十七、错误处理

技术错误不能直接暴露给普通用户。

系统内部需要区分：

* 没有可分析内容；
* 输入过长；
* 请求失败；
* LLM 超时；
* LLM 返回异常；
* 服务暂时不可用。

Extension 最终只需要展示适合用户理解的状态。

例如：

> 暂时没读懂这里的空气。

而不是直接展示后端异常信息。

---

# 十八、隐私

读空气会处理用户当前浏览的网页内容，因此隐私是重要技术约束。

MVP 遵循：

1. 只在两种时机把页面内容发送到服务器：用户主动请求分析，或进入用户逐个授权过的网站；扩展会在本地比对讨论文本以判断结果是否过期，比对不会上传内容。
2. 不读取浏览历史。
3. 不在后台持续监控用户浏览行为。自动打开只覆盖用户授权过的站点：扩展不申请 `tabs` 权限，未授权站点的地址对它不可见。
4. 不因为使用读空气而建立完整的浏览画像。
5. 服务器不保存讨论内容：不落库，日志只记失败原因。扩展只在浏览器本地留一份分析结论，同一段内容不再重复分析，浏览器关闭即清空。
6. 明确告知用户页面内容会发送到服务器进行 AI 分析：分两处说，各自解决一半。浮窗在第一次把页面文字发出去时说明一次——以"隐私声明"为标题独自成区、排在设置区下方，只挂在真的发出过请求的结局上（成功或失败都算，没读到内容而不发请求的不算）。设置里另有一行"隐私声明"入口，点开就地展开完整声明（什么时候发、谁在判断、最后一环留给谁、以及用户能怎么办），再点收起。两处措辞取自同一份文案，且都不绑定当下这个页面。
7. 站点访问权限按站点逐个申请，用户可以在扩展设置里随时收回。

服务器侧不保存讨论内容；模型服务提供方自身的留存策略取决于所选服务，上线前确认。

# 十九、测试与验证

技术验证重点不是测试数量，而是验证核心链路可靠。

### Extension

单元测试（`npm run test`）覆盖不依赖页面渲染的那部分：

* 取样窗口：短于窗口原样给出、长于窗口时首尾都在、不切半行、每一截里都取到行；
* 结果过期与整段被替换的判定；
* 站点期望表、站点标识与权限模式的换算、授权名单的读写；
* 后端返回体的校验；
* 两处存储契约：会话缓存记什么、隐私声明只取走一次。

依赖真实渲染的部分（shadow root、懒加载、可见性判断）仍以浏览器实测为准：

* 页面内容能够正常获取；
* 浮窗正常显示；
* 分析状态正确切换；
* API 异常能够正确处理。

### Backend

验证：

* API 输入校验；
* Application 核心流程；
* LLM 输出结构校验；
* Flame Intensity 范围约束；
* 异常情况。

### AI

建立一组固定文本样本，覆盖五档中的各档（平和、争论明显、对立明显、骂战激烈），另加一段无法判断的内容；跑真实模型，断言落在预期档位——见 `FlameIntensityEvaluationTest`，默认不进 CI，改口径或换模型时手动跑。

样本是自造的：真实页面的评论属于别人，不适合固化进仓库，也会随站点改版过期。真实样本只用于校准，用完即弃（做法见开发记录）。

```text
平和讨论
↓
轻度争论
↓
明显冲突
↓
激烈骂战
```

观察不同版本 Prompt 或模型调整后，结果是否出现明显退化。

AI 质量验证是本项目非常重要的一部分。

# 二十二、技术演进方向

如果 MVP 得到验证，未来可能出现：

```text
                    读空气
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
     更多指标       历史变化       自定义指标
        │              │              │
        └──────────────┼──────────────┘
                       ↓
                  更大的空气模型
                       ↓
                跨网页 / 跨社区
```

技术架构应该允许这些方向逐步加入，但不应为它们提前实现复杂基础设施。

---

# 二十三、当前技术核心问题

读完这份文档后，当前真正需要解决的技术问题只有几个：

> **1. 如何可靠地从网页中提取有价值的文本？**

> **2. 如何让 LLM 对“骂战激烈程度”给出稳定、可解释的判断？**

> **3. 如何让 Extension 与 Backend 形成足够简单、可靠的产品闭环？**

> **4. 如何在保持后端架构清晰的前提下，不引入超出验证所需的工程复杂度？**

MVP 的技术工作应该围绕这些问题展开，而不是提前解决未来的问题。
