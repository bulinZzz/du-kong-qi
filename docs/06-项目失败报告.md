# 读空气 项目失败报告

读空气于 2026-09-21 停止开发。这份文档只回答一个问题：为什么停止。

它与仓库里其他文档的分工不同：技术状态见 [03-技术设计.md](03-技术设计.md)，开发过程中的做法与理由见 [04-开发记录.md](04-开发记录.md)，没有执行的上线方案保留在 [05-上线运营.md](05-上线运营.md)。产品本身是什么，见 [README](../README.md)。

本文对四类信息作区分：**事实**是可核对的结果，**观察**是开发过程中看到的现象，**判断**是据此作出的取舍，**推测**是没有验证的猜想。项目没有正式上线，也没有形成真实用户样本，因此凡涉及用户意愿的结论都只能是推测，本文不会把它写成事实。

---

## 一、项目结论

**项目已停止：不再开发，不上线，不购买云服务器，不继续申请任何浏览器商店。**

停止日期：**2026-09-21**。

仓库保持开源，代码、文档与开发记录不删除。停止的原因不是功能无法完成——核心链路已经在真实页面上跑通；原因是**核心体验与用户进入路径之间没有形成可接受的闭环**，而闭环的代价超出了这个项目愿意承担的范围。判断过程见第四节。

---

## 二、项目最初想解决什么问题

互联网上的讨论空间有自己的“空气”：一个页面表面上只是文字，读起来却可能是轻松温暖的，也可能是紧张的、荒诞的，或者已经充满火药味。

当时的观察是，已有工具大多在判断内容是什么、情绪是正面还是负面、某句话是否具有攻击性，而“整个空间现在是什么感觉”没有被单独对待。

第一阶段因此只回答一个问题：

> **这个网页现在到底有多大火药味？**

输出为 0～100 的冲突与敌意程度，配一句简短的空气判断。

第一阶段刻意不追求完整的空气模型。它要验证的是最核心的产品假设，也就是 README 里定下的那一条：**用户是否认为“让 AI 帮自己读空气”有趣、有价值。** 衡量标准也是当时写下的那句话——用户看到结果后会不会产生“卧槽，确实”的反应。

从这里可以看出，这个项目从一开始就不是一个待上线的完整产品，而是一次产品假设的验证尝试。后文的所有判断，都是在这条前提下作出的。

## 三、最终采用的产品形态

```text
浏览器扩展  ──▶  后端服务  ──▶  大模型
```

扩展读取用户当前浏览的页面、接收操作、展示结果；后端整理内容、组织分析、校验结果；大模型是外部能力，不属于产品自身的业务核心。

浏览器扩展不是偶然选择，而是核心体验的一部分：

* 输入是**当前页面**的上下文，用户不需要描述自己看的是什么；
* 期望是**即时**得到结果，不是排队等待；
* 用户不应该复制、粘贴内容，也不应该知道“文本提取”这件事存在；
* “在讨论现场直接读空气”本身就是体验——离开那个页面，再去别处问一次，得到的是另一件产品。

第三点是这个形态成立与否的关键：把内容复制到别处，等于把“读空气”变成“分析这段文字”，产品的价值主张会随之改变。

## 四、为什么最终停止

这一节的因果链，是本次停止的全部依据：

```text
核心体验依赖浏览器扩展
        │
        ▼
目标用户浏览器高度分散
        │
        ▼
不同浏览器有各自的分发入口与商店
        │
        ▼
普通用户从“看到内容”到“装上并用起来”的摩擦明显
        │
        ▼
继续覆盖浏览器会带来持续的审核、兼容与维护成本
        │
        ▼
Web 版显著降低摩擦，但保留不住核心体验
        │
        ▼
没有找到成本可接受的产品进入路径
        │
        ▼
停止项目
```

链条的每一段依据不同，需要分开看：

**事实。** 第一版的支持范围定在 Chrome 与 Edge，安装入口只留 Chrome Web Store 一个。这个决定写在 [03-技术设计.md](03-技术设计.md) 第三节，理由是正文提取依赖 `Element.checkVisibility()`（Chromium 105+），缓存与浮窗状态依赖 `chrome.storage.session` 与 `setAccessLevel`（102+）。

**观察。** 开发过程中看到的几件事：Edge 用户从 Chrome Web Store 安装，第一次要多点一次“允许来自其他商店的扩展”，企业受管设备还可能被策略挡掉；360 系浏览器的内核版本未知，这类内核长期滞后；Chrome 与 Edge 自 137 起移除了 `--load-extension`，往正式版浏览器里塞扩展已经没有可用的命令行路径，手工安装只能走扩展页的“加载已解压的扩展程序”。这些都不是推断，是当时实测与查证的结果。

**判断。** 上面这些观察放在一起，指向的不是某个浏览器的兼容问题，而是**扩展这种形态不提供统一的分发入口**：每多覆盖一个浏览器，就多一套商店、审核、兼容与维护。而目标用户主要来自中国大陆，浏览器分布并不集中——这意味着覆盖成本不是一次性投入，而是随着覆盖面扩大持续增加。在这条路径上，产品复杂度不只来自代码。

**推测。** 用户是否愿意跨过安装门槛、装上之后是否觉得有用，这两件事**从头到尾没有验证过**。项目没有上线，也就没有安装量、活跃数据或用户反馈。因此不能反过来说“用户不愿意装扩展”或“用户不需要读空气”——那两句话没有证据支撑。

**另一个被否掉的方案。** Web 版能显著降低分发摩擦：给一个网址就能用，不需要装任何东西。但它必须让用户先把内容放到网页上，而第三节列出的第三点与第四点正是在这个动作里丢掉的——“不用复制粘贴”不再成立，“在讨论现场直接读空气”变成了一次手工搬运。经过产品判断后，这个方案不作为替代。

**为什么没有先做一次低成本验证。** 这里有一个自然的质疑：既然结论建立在“尚未验证”之上，为什么不在停止前把扩展包私下发给几个人，或者发一篇帖子附上下载链接，用很低的成本测一次安装意愿？

原因是这个产品没有“低成本验证”这一档。扩展自身不持有模型密钥，也不包含任何分析能力（见 [03-技术设计.md](03-技术设计.md) 第十三节），页面文本必须由后端接住再交给模型。因此陌生人拿到扩展包也无法使用：他本机没有后端，请求打不通，看到的只会是一次失败。要让他真正看到一次结果，后端就必须已经跑在公网——域名、证书、密钥、成本护栏缺一不可。想绕开这一点只剩一条路：让试用者从 GitHub 拉源码、自备模型 API 密钥、在本机启动后再加载扩展。愿意走完这条路的人太少，找不到这样的人也就无从取样。

于是“第一次真实用户验证”与“上线投入”在这个产品形态里是同一件事：**没有服务器，就没有任何可用的形态**。这一点加重了上面的判断——继续推进不是“再花一点”，而是要先跨过一整段线上投入，才能拿到第一份用户证据。

核心判断可以总结为一句话：

> **当前项目的失败，不是“功能没有做出来”，而是“核心体验与用户进入路径之间没有形成可接受的闭环”。**

值得注意的是这个结论出现的时间点：它出现在正式用户验证之前。项目暴露的是一个**进入问题**，而不是一个**价值问题**——两者的证据要求完全不同，把它们混为一谈就会得出错误的结论。

## 五、哪些事情已经完成

以下按开发记录与代码整理，只列能力，不复述实现细节。

**后端分析链路**

* 对外只有一个分析接口，公开契约只收页面文本；
* 输入规范化与长度兜底，结果结构化并逐项校验，分值越界判为非法结果而不夹取；
* 失败区分“内容不足”与“服务不可用”，各自对应不同的提示、状态码与日志级别；
* 模型返回“读不出来”时作为一等结果处理，不折算成分数；
* 评分口径集中在单个提示词类里，五档 rubric 与评测基线可手动运行，做过一次基于真实讨论的校准；
* 对外接口的准入与限流：来源校验，以及按 IP 每分钟与全局每日两道配额，均已实现并通过冒烟验证；
* 每次调用留下一行用量日志（站点、状态、耗时），不含正文与完整地址。

**浏览器扩展**

* Manifest V3 骨架：点击工具栏时注入内容脚本，请求由后台 Service Worker 发出，权限按站点逐个申请；
* 页面内容提取：逐节点下钻 shadow root，以 `checkVisibility()` 判断渲染状态，站点期望表加通用回退（B 站、知乎、微博移动站）；
* 真实页面问题：触发懒加载的“无感搬运”、失败时退回用户触发的真实滚动、评论区优先于整页、页面自身界面文字的按行过滤；
* 取样窗口：整段摊开的多窗口、按行切分、条数口径跟随站点术语；
* 结果过期检测：按行集合比对，把“内容变多”与“被分析那段被替换”分开判断；
* 分析状态与失败状态各自成态，“读不出来”同样是一等结果；
* 浮窗：Shadow DOM 隔离、拖动、八向缩放、折叠为圆片、位置与形态记入会话存储；
* 授权流程：设置区嵌在浮窗内、失败时退到独立窗口、按站点记录授权名单；
* 隐私告知：第一次真正发出内容时说明一次，设置里另有可查证入口；
* 会话级分析缓存，键取内容哈希；
* 生产地址注入与商店上传包脚本，打包时拒绝非 https 与缺省值；
* 后端同域提供隐私政策页。

**工程与验证**

* 前端 TypeScript + Vite、后端 Java + Spring Boot 的前后端分离结构；
* 后端按整洁架构分层，模块间以公开契约隔离，架构约束有测试守护；
* 扩展单元测试覆盖纯数据部分，依赖真实渲染的部分以浏览器实测为准；
* 后端覆盖输入校验、用例编排、模型输出校验与异常映射的测试；
* CI 中运行两端的构建与测试，评测基线默认不进 CI，改口径或换模型时手动跑；
* 开发记录中沉淀出的工程判断，见 [04-开发记录.md](04-开发记录.md) 第二部分。

用一句概括这一节：

> **项目停止，不代表前期开发没有价值。**

这里的价值有两个部分。一部分是代码本身：从网页中可靠提取讨论文本、处理 shadow root 与懒加载、判断讨论是否发生变化，这些经验可以直接迁移到别的形态上去。另一部分是判断依据：哪些设计必须由实测决定、哪些地方不该替用户做决定、哪些成本是被低估的——这部分写在开发记录里，比代码更耐用。

## 六、哪些事情明确没有做

以下事项**因项目终止，不再执行**，不作为后续计划保留：

* 没有购买云服务器，没有部署过后端服务；
* 没有为线上环境编写 systemd unit 或 Dockerfile；
* 没有配置域名、反向代理与 HTTPS，没有实际演练过回滚；
* 没有申请 Chrome 开发者账号，没有上传或发布任何浏览器商店；
* 没有形成真实用户规模，没有安装量、活跃数或留存数据；
* 没有建立正式运营数据，没有用户反馈渠道；
* 没有验证商业化路径；
* 没有扩展到 Chrome 与 Edge 之外的浏览器。

这些不是“以后再做”的清单，而是本次探索没有到达的边界。把它们明确写下来，是为了让读者能分清仓库里哪些是已经跑通的代码，哪些只是当时写好的方案——[05-上线运营.md](05-上线运营.md) 属于后者。

## 七、真正沉淀下来的经验

以下判断来自开发过程，[04-开发记录.md](04-开发记录.md) 中有对应的具体经过；这里只留结论。

**技术可行不等于产品可进入。** 核心链路在真实页面上跑通，与用户能不能方便地开始用它，是两件独立的事。前者完成，不能说明后者会成立。

**核心体验不能只看实现成本，还要看用户第一次接触它的路径。** 评估一个功能时，容易只算“做出来要多少工作”，而忽略“用户要跨过多少步才能碰到它”。后者往往才是决定性的。

**验证成本不总是“把东西做出来”的成本，它有时等于上线成本。** 常见做法是先花很小的代价试着接触用户，再看要不要继续。但有些形态没有这一档：读空气的扩展离开后端就没有任何能力可用，任何真实试用都要求先有服务在公网跑着。当验证的最小单位本身就包含部署时，“先小范围试一下”与“正式上线”合并成了一步，也就没有中间档可退。判断要不要继续投入时，这一项必须一起算。

**分发渠道本身就是产品设计的一部分。** 渠道不是一个投放动作，它决定了用户要付出什么、也决定了产品能被谁用到。选择浏览器扩展作为载体，等于同时选择了它的分发方式。

**对独立开发者来说，产品复杂度不只来自代码。** 平台限制、商店审核、权限说明、兼容矩阵、安装路径，都是需要持续投入的部分，且不随代码质量下降。

**不要为了“理论上的用户覆盖率”提前支持一堆平台。** 平台扩展应当由真实需求推动。在需求出现之前增加覆盖面，付出的是确定的成本，换来的是不确定的收益。

**在没有验证用户愿意跨过安装门槛之前，不应继续增加兼容与分发成本。** 这是本次停止的直接依据，也是最值得记住的一条。

**一个想法如果只能在某种载体上成立，那么这个载体本身就是产品成立条件，而不是技术实现细节。** 读空气的核心价值依附于“在讨论现场即时分析”，因此浏览器扩展是它的成立条件之一，而不是一个可以随时替换的实现选择。把载体当细节，就会误判替换它的代价——Web 版方案正是在这里被否掉的。

## 八、这次失败不能得出什么结论

本次停止**不能**说明以下任何一件事：

* 不能说明用户不需要“读空气”这类工具；
* 不能说明浏览器扩展没有市场；
* 不能说明 AI 产品没有价值；
* 不能说明中国大陆用户不接受插件；
* 不能说明这个想法未来永远没有机会。

原因很直接：项目没有上线，没有真实用户样本，涉及用户意愿的每一个结论都缺少证据。第四节里被标记为“推测”的部分，在本节同样只是推测。

能够得出的只有一条，而且它描述的是资源约束而不是市场判断：

> **以当前的目标用户、当前的分发环境与当前的资源约束，继续推进读空气的成本已经超过我愿意承担的范围。**

---

## 九、未来什么变化可能使项目重新成立

这一节不是待办清单，而是**重新启动的条件**。下面任何一条单独出现都不够，至少需要几条同时成立。

* 浏览器扩展的分发方式发生明显变化，安装摩擦显著下降；
* 目标用户的浏览器结构发生变化，出现一个足够集中的默认入口；
* 出现低摩擦的统一安装入口，能够覆盖多个浏览器与商店；
* 能够通过其他方式获得网页上下文，同时保住“在当前页面上即时分析”这一核心体验；
* 出现一个比当前方案成本明显更低的产品载体。

在这些条件满足之前，不重新启动项目。
