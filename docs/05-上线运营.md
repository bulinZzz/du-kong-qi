# 读空气 上线运营

从准备发布到跑起来之后，这份文档管这一段：上线前该提前做完什么、部署怎么做、上线后看什么、怎么知道这东西有没有用。

当前的设计与结构见 [03-技术设计.md](03-技术设计.md)，做法与理由见 [04-开发记录.md](04-开发记录.md)。

## 一、上线前

这四件事都不依赖服务器，最花时间的是第一件。

**商店材料。** Chrome 开发者账号（一次性 5 美元）、3–5 张 1280×800 截图、商店描述、权限理由（`activeTab` 与 `scripting` 各自为什么需要）、数据使用声明表。隐私政策地址由后端提供（见部署一节），截图趁界面刚定稿时做最省事。

**真机回归。** 装上新扩展，B 站、知乎、微博各跑一次。界面、图标、请求头这类改动，只有拉进真扩展里才算验过——用注入脚本验渲染，覆盖不到工具栏、授权页与后台 Service Worker。

**模型密钥与成本。** 确认密钥可用、账户有余额，并按服务商当前单价核一遍每日上限。每次分析大约送出一万字，上限全用满是什么量级，上线前应当心里有数。默认值见 [application.yml](../apps/backend/src/main/resources/application.yml)。

**进程守护。** 仓库里既没有 systemd unit 也没有 Dockerfile，上线当天要现写。想省这一步就提前写好，否则服务器重启后服务不会自己起来。

域名可以同时买好并解析到服务器；HTTPS 由 certbot 办，见下文。

## 二、部署

后端为无状态可执行 jar：不依赖数据库，也不将讨论内容落盘。部署只需一台最小规格的云主机。

### 打包与运行

```bash
cd apps/backend
mvn -DskipTests package
ATMOSPHERE_LLM_API_KEY=<模型密钥> java -jar target/*.jar
```

| 环境变量                       | 说明                                                                            |
| -------------------------- | ----------------------------------------------------------------------------- |
| `ATMOSPHERE_LLM_API_KEY`   | 模型服务的密钥，必填                                                                    |
| `API_GUARD_ALLOWED_ORIGINS` | 允许的请求来源，上线时填扩展自身的来源 `chrome-extension://<扩展 ID>`；留空则不校验来源，启动时打一条警告               |
| `API_GUARD_PER_IP_PER_MINUTE` | 单个来源 IP 每分钟的请求数                                                              |
| `API_GUARD_DAILY_LIMIT`    | 全部请求的每日上限，超出后不再受理                                                             |

限流两项的默认值与取值理由见 [application.yml](../apps/backend/src/main/resources/application.yml) 的注释，该处为唯一来源。

### 反向代理与 HTTPS

反向代理**必须**写入 `X-Forwarded-For`。应用据此识别来源 IP（对应配置 `server.forward-headers-strategy`）；缺失该头时，来源 IP 一律取到代理地址，按 IP 的限流会误伤全部调用方。

Nginx 先只声明 80 端口。`$remote_addr` 为直连对端地址，以覆盖方式写入，使客户端自带的值不参与取值：

```text
server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

安装 `nginx`、`certbot` 与 `python3-certbot-nginx` 后执行 `sudo certbot --nginx -d api.example.com`：certbot 据此补全证书与 443 监听，并将 80 改为跳转；证书续期由其附带的 systemd timer 承担。

### 首次上线顺序

1. 购买域名并解析到服务器；
2. 部署 jar（systemd 或 Docker），配置模型密钥；
3. 配置反向代理与 HTTPS，确认 `https://<域名>/privacy` 可访问；
4. 将扩展来源填入 `API_GUARD_ALLOWED_ORIGINS`；
5. 生成上传包：`$env:BACKEND_ORIGIN='https://<域名>'; npm run package`，产物位于 `apps/extension/release/`；
6. 将 zip 上传至 Chrome 开发者后台，隐私政策地址填写 `https://<域名>/privacy`。

扩展 ID 在上传首个版本后固定，因此第 4 步与第 6 步的先后不可调换。第 4 步填完必须重启服务才生效——配置在启动时读入。

### 一台机器上放多个项目

本项目用 Spring Boot 的默认端口 8080。要把别的项目也放到这台机器上时，别继续依赖默认值：把端口显式写进配置、让服务只监听回环地址，再记一张"域名 → 端口"的台账。8080 是一大批软件的默认口（Tomcat、Jenkins、各类管理面板），被别的进程先占住时服务起不来，而报错只说端口被占，不会告诉你是谁占的。外部只认域名，端口是内网实现细节——用容器时每个项目内部都可以继续用 8080，只在宿主机上映射成不同的口。

## 三、上线后

每次调用接口会留下一行日志，格式与含义见 [03-技术设计.md](03-技术设计.md) 的"用量记录"：

```bash
journalctl -u <服务名> | grep 接口调用
```

按站点汇总，就能看出哪个站点读不到内容：

```bash
journalctl -u <服务名> | grep -o '站点=[^ ]* 状态=[0-9]*' | sort | uniq -c | sort -rn
```

站点记成 `unknown` 的行来自还没有带上站点的旧版扩展——看到它说明商店里还有老版本没更新。

**现在没有的东西，比以为有监控更重要。** 没有告警，当日额度用满只有一条 warn 日志；没有失败率或用量面板；日志是唯一的观测手段。上线初期建议每天看一次上面的命令，重点看两类：5xx 说明分析真的坏了；429 说明有人在被挡，可能是有人猛按，也可能是共享出口 IP 的正常用户被误伤。422 多不必紧张——那是"这段讨论太少"，本身是正常结果。

**要是被人刷了**：把每日上限调小并重启，能立刻止血；来源名单清空等于不校验，反过来填错也会挡住所有人。限流计数放在内存里，重启即清零——这一点在"止血"时反而有用。

## 四、用户反馈

免费又没有账号，产品里就没有任何自然的接触点：用户不会写邮件，也没地方留联系方式。所以别指望一个"通用反馈箱"，它一定会空着。能改变判断的信号只有三个，各自的办法都不一样：

| 要回答的问题 | 怎么答 |
| --- | --- |
| 有人第二次用吗 | 商店后台的活跃用户数。零成本，也最接近"这东西有没有用" |
| 分数准不准 | 浮窗上加"准 / 不准"（尚未做）：一次点击，回传分数、等级与站点 |
| 哪些页面读不到 | 服务端按站点的用量记录（已有，见上一节） |

**隐私边界**：任何回传都不带讨论正文，这是隐私政策里的承诺。若想知道"这条为什么判 87"这类样本，就让用户在浮窗上**显式勾选**"连同这段文字一起发送"，默认不勾——可选、可见、用户知道自己在给什么，既不违背声明，也拿得到语料。

**别做的事**：通用反馈箱、必填问卷、评分弹窗。免费产品里浮窗是唯一能形成习惯的接触点，反馈入口必须在那里，一键、可选、不打断。

**有一点量之后**：商店页的"支持"链接指向一个落地页或邮箱；再到 V2EX、少数派、小红书发一篇介绍。对自带话题的产品，公开评论区的反馈量通常大于产品内埋点，而且顺带获客。这一步要等手上有截图与真实案例，那时效果差很多。
