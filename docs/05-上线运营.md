# 读空气 上线运营

一个产品从本机上的代码变成线上能用的东西，要依次经过几层。这份文档先给这个模型——每一层在解决什么、判据是什么、最容易漏的是什么；再给读空气在这一层里具体怎么做。

读空气只是这个模型的一个实例：换一个产品，层不变，实例换掉。所以读它的时候重点在层，命令只是这一层的落地细节。

当前的设计与结构见 [03-技术设计.md](03-技术设计.md)，做法与理由见 [04-开发记录.md](04-开发记录.md)。

## 一、产物与配置

**要回答**：产物是什么形态（可执行文件、容器镜像、静态文件）？它依赖哪些外部东西，这些东西从哪来？

**判据**：在一台没有 IDE、没有本机依赖的机器上，只靠产物加上注入的配置就能起来。

**最容易漏**：把密钥、地址、调试开关写进代码或仓库；产物里混进只在本机成立的东西（本机地址、sourcemap、测试用的值）。

**读空气**：一个无状态可执行 jar，不依赖数据库，也不把讨论内容落盘。

```bash
cd apps/backend
mvn -DskipTests package
ATMOSPHERE_LLM_API_KEY=<模型密钥> java -jar target/*.jar
```

| 环境变量                       | 说明                                                                            |
| -------------------------- | ----------------------------------------------------------------------------- |
| `ATMOSPHERE_LLM_API_KEY`   | 模型服务的密钥，必填                                                                    |
| `API_GUARD_ALLOWED_ORIGINS` | 允许的请求来源，上线时填扩展自身的来源 `chrome-extension://<扩展 ID>`；留空则不校验来源，启动时打一条警告               |
| `API_GUARD_PER_IP_PER_MINUTE` | 单个来源 IP 每分钟的请求数                                                              |
| `API_GUARD_DAILY_LIMIT`    | 全部请求的每日上限，超出后不再受理                                                             |

## 二、入口

**要回答**：外部只认什么（域名还是地址加端口）？谁负责 TLS？服务端拿到的客户端 IP 从哪来？

**判据**：`https://<域名>` 打得开、80 会自动跳过来，而应用本身不对公网暴露。

**最容易漏**：以为服务器看到的对端就是用户（反代之后不是，真实 IP 要靠 `X-Forwarded-For` 带进来）；把应用端口暴露在公网；证书忘了续期。

**读空气**：Nginx 只声明 80 端口，`$remote_addr` 以覆盖方式写入，证书交给 certbot。外部只认域名，端口是内网实现细节。

```text
server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

安装 `nginx`、`certbot` 与 `python3-certbot-nginx` 后执行 `sudo certbot --nginx -d api.example.com`：certbot 补齐证书与 443 监听，并把 80 改为跳转；续期由它自带的 systemd timer 承担。

一台机器上要放多个项目时，别依赖默认端口：把端口显式写进配置、让服务只监听回环地址，再记一张"域名 → 端口"的台账。用容器时每个项目内部都可以继续用同一个端口，只在宿主机上映射成不同的口。**读空气现在用 Spring Boot 的默认端口 8080。**

## 三、护栏

**要回答**：这个接口后面挂着按量计费的东西吗？最坏情况下一天花多少钱？被刷时怎么止血？

**判据**：能说出"最坏一天多少钱"，并且能在十分钟内把闸门关小。

**最容易漏**：只做鉴权不做配额（或反过来）；把闸门做成会误伤正常用户——共享出口 IP（校园网、公司网、移动网络）的人会共用一份额度；根本不知道自己成本的上限在哪。

**读空气**：两道闸，来源校验加按 IP 与每日计数，说明见 [03-技术设计.md](03-技术设计.md) 的"对外接口的准入与限流"。两个数字都是拍出来的初值，上线前按服务商当前单价核一遍：每次分析大约送出一万字，上限全用满是什么量级，应当心里有数。

**被刷时的止血动作**：调小每日上限并重启即可；限流计数在内存里，重启即清零。

## 四、常驻

**要回答**：进程崩了谁拉起？机器重启后它会不会自己回来？日志写到哪、怎么找？

**判据**：`reboot` 之后不用登录服务器手动敲命令，服务自己起来。

**最容易漏**：用 `nohup` 或者在 IDE 里跑着（关掉窗口就没了，端口还占着）；日志跟着终端走，断开就丢；以为服务器会把它记住。

**读空气**：**还没有 systemd unit，也没有 Dockerfile——这是目前最大的缺口**，上线当天要现写。想省这一步就提前写好放仓库里。

## 五、观测

**要回答**：出问题时你多快知道？靠什么知道？

**判据**：能回答"昨天失败了多少次、都是哪一类"，而且不依赖用户来告诉你。

**最容易漏**：以为有监控（其实只有日志）；日志里没有可聚合的字段，只能肉眼翻；把正常结果当成错误去告警。

**读空气**：每次调用留一行用量，格式见 [03-技术设计.md](03-技术设计.md) 的"用量记录"。

```bash
journalctl -u <服务名> | grep 接口调用
journalctl -u <服务名> | grep -o '站点=[^ ]* 状态=[0-9]*' | sort | uniq -c | sort -rn
```

重点看两类：5xx 说明分析真的坏了；429 说明有人在被挡，可能是有人猛刷，也可能是共享出口 IP 的正常用户被误伤。422 多不必紧张——那是"这段讨论太少"，本身是正常结果。站点记成 `unknown` 的来自还没带上站点的旧版扩展，说明商店里还有老版本没更新。

**现在没有告警**，日志是唯一手段。上线初期每天看一次上面两条命令。

## 六、分发

**要回答**：用户在哪拿到它？上架要交什么材料？版本怎么更新？

**判据**：一个陌生人能在不看仓库的情况下装上并跑通。

**最容易漏**：把审核材料留到最后一刻（截图、描述、权限理由、数据使用声明都要时间）；忘了隐私政策地址；版本号与产物对不上；以为扩展 ID 可以事先决定——它由渠道在第一次上传时生成，所以"上传"与"发布"要拆成两次动作（见最后一节）。

**读空气**：Chrome 开发者后台，需要账号（一次性 5 美元）、3–5 张 1280×800 截图、商店描述、权限理由（`activeTab` 与 `scripting` 各自为什么需要）、数据使用声明表，隐私政策地址用 `https://<域名>/privacy`。截图趁界面刚定稿时做最省事。

**范围与入口**：第一版只上 **Chrome Web Store 这一个入口**，只支持 Chrome 与 Edge。Edge 用户从同一个商店安装，第一次会弹出"允许来自其他商店的扩展"，点允许即可；企业受管设备可能被这条策略封掉，属少数情况，不为它另开渠道。其余浏览器暂不支持。

## 七、反馈

**要回答**：没有账号、没有收费时，用户的想法从哪来？哪些信号能改变你的决定？

**判据**：能说出"这东西有没有用"的依据，而且是数字，不是感觉。

**最容易漏**：做通用反馈箱（一定会空着）；把请求数当成使用人数（同一段内容命中缓存后不再请求）；为了拿反馈越过隐私承诺。

**读空气**：能改变判断的只有三个信号，各自的办法不一样。

| 要回答的问题 | 怎么答 |
| --- | --- |
| 有人第二次用吗 | 商店后台的活跃用户数。零成本，也最接近"这东西有没有用" |
| 分数准不准 | 浮窗上加"准 / 不准"（尚未做）：一次点击，回传分数、等级与站点 |
| 哪些页面读不到 | 服务端按站点的用量记录（已有，见"观测"一节） |

**隐私边界**：任何回传都不带讨论正文，这是隐私政策里的承诺。若想知道"这条为什么判 87"这类样本，就让用户在浮窗上**显式勾选**"连同这段文字一起发送"，默认不勾——可选、可见、用户知道自己在给什么。

**别做的事**：通用反馈箱、必填问卷、评分弹窗。免费产品里浮窗是唯一能形成习惯的接触点，反馈入口必须在那里，一键、可选、不打断。

**有一点量之后**：商店页的"支持"链接指向一个落地页或邮箱；再到 V2EX、少数派、小红书发一篇介绍——对自带话题的产品，公开评论区的反馈量通常大于产品内埋点，还顺带获客。这一步要等手上有截图与真实案例。

## 八、变更

**要回答**：改完怎么上线？发坏了多久能退回上一个版本？

**判据**：能说出回滚的具体动作，并且演练过一次。

**最容易漏**：只在本地改完就以为上线了（发布是一次动作，不是保存文件）；没有可退的旧版本；一旦有了数据库，回滚就变成真正的难题——迁移脚本走了就得能倒回来。

**读空气**：无状态、无数据库，回滚就是把上一版的 jar 换回去重启，一次几十秒。但**还没有实际演练过一次**，这一点该在上线前补上。

## 九、把各层串起来：首次上线顺序

这里有个跨层的依赖要绕开：**护栏要知道扩展 ID，而扩展 ID 由分发渠道产生**。所以"上传"必须拆成两次——先传一次拿到 ID，配好护栏，再回来补材料、提交审核。商店在第一次上传时就把 ID 定下来，之后改不了，也没法事先预定：manifest 里写 `key` 不影响商店分配的 ID，那个字段只管开发期加载出来的 ID。好在草稿那一次不必等服务器——域名定下来之后就能先传一次，把 ID 拿到手，护栏的配置也提前备好了。

1. 购买域名并解析到服务器；
2. 部署 jar（systemd 或 Docker），配置模型密钥；
3. 配置反向代理与 HTTPS，确认 `https://<域名>/privacy` 可访问；
4. 生成上传包并上传到开发者后台，**先不提交审核**：`$env:BACKEND_ORIGIN='https://<域名>'; npm run package`，产物位于 `apps/extension/release/`。商品一创建，扩展 ID 就确定了；
5. 把那个 ID 填进 `API_GUARD_ALLOWED_ORIGINS` 并重启后端——配置在启动时读入；
6. 在后台补完商店信息（描述、截图、权限理由、数据使用声明、隐私政策地址 `https://<域名>/privacy`），装一次这个包做真机确认，然后提交审核。

第 5 步与第 6 步之间那次真机确认不能省：前面几步都只是配置，只有它证明"扩展带上的 ID、后端认的来源、域名解析、证书、代理"这几件事真的合得上。

## 十、其中哪几层不必等服务器

分发与反馈的材料、产物的自检、护栏的取值、常驻的配置文件——都不依赖服务器，买之前就能做完，其中第一件最花时间：

- **商店材料**：账号、截图、描述、权限理由、数据使用声明；
- **真机回归**：装上新扩展，B 站、知乎、微博各跑一次。界面、图标、请求头这类改动，只有拉进真扩展里才算验过——用注入脚本验渲染，覆盖不到工具栏、授权页与后台 Service Worker。装的时候只能在扩展页点"加载已解压的扩展程序"：Chrome 与 Edge 自 137 起移除了命令行的侧载开关；
- **模型密钥与成本**：确认密钥可用、账户有余额，核一遍护栏的取值；
- **进程守护文件**：systemd unit 或 Dockerfile，写进仓库就等于顺手补上了第四层的缺口。

买服务器当天再做这些，就是把能提前做完的事挤到最忙的一天。
